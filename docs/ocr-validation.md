# OCR 검증 및 검토 흐름

2026-09-29 최신 품질 기준(D-148)은 여러 사진을 넣은 뒤 **OCR 오류 때문에 사용자가 장비 값을 고치거나 누락값을 채우는 일 없이 정확히 등록하는 것**이다. 사진 개수는19장에 고정하지 않는다. 수동 수정 후 정확해진 결과를 무수정 인식 성공으로 집계하지 않는다.

2026-10-01 후속 [장비 사진 판독 정확도 개선 계획](ocr-accuracy-improvement-plan.md)은 미식별 행 재인식·참고 항목 분류·숫자/% 검증·전체 옵션 누락 검사와 단계별 통과 기준을 정리한다. 계획 작성 완료이며 구현·정확도 검증 합격이나 기존 미통과 실험의 활성화를 뜻하지 않는다.

후속 구현에서는 실패 판독 관측과 공통 행 복구 Module을 추가했다. 기본 경로의19장 결과는13장16줄 확인 필요로 유지됐으며, 사용자 확인한 돋움 자료의 여러 판독/합성 학습 후보는 수치 정확도 기준을 통과하지 못했다. 새 자동 확정 후보는 개발 호출에만 두고 일반 팩토리/UI에서 활성화하지 않는다. 전체 계획과 무수정 목표는 미완료이며 상세 상태는 해당 계획의 첫 구현 결과를 따른다.

아래 처리·검토 설명은 현재 구현의 안전장치다. 미해결 값을 사용자에게 수정받는 기능이 남아 있다는 사실과 최신 목표 달성 여부를 구분한다. 정확성이 검증되지 않은 값을 자동 확정하거나 검토 경고만 없애는 것은 개선이 아니다.

**검증 복구 후보의 활성화 기준은 미통과다.** 기본 인식은 D-150을 유지하며 후보는 명시적인 개발·시험용 생성자 옵션에서만 실행한다. 원본20장 비교에서 후보 v4의16장 통과는 기존17장보다 회귀했고, 실제 Paddle의 부분 dim 숫자 합성 반례를 후보 판정 모듈에 넣었을 때8건을 잘못 채택했다. 합성56사례와 게임 원본/독립 사용자 사진을 구분한다. 서로 다른 보기의 일치만으로 사라진 앞/뒤 glyph를 검증할 수 없으므로, 기본 활성화·전체 무수정 목표 달성을 완료로 기록하지 않는다. 상세 상태는 [실험 계획과 미통과 근거](ocr-verified-recovery-plan.md)를 따른다.

## 처리와 확인

- OCR 모듈·모델·이미지 전처리 작업자의 준비 실패는 사진 판독 결과와 구분한다. 사이트/개발 서버 연결과 인식 기능 준비 상태를 안내하고 같은 사진으로 재시도할 수 있게 한다. 모든 실행 오류를 이미지 옵션 미인식으로 표시하지 않는다.
- 현재 능력창 사진 등록은 제공하지 않는다. 순수 주/부스탯 숫자를 직접 입력하며 텍스트 붙여넣기를 지원한다. 장비·후보 사진의 파일 선택·Ctrl+V·드래그 경로는 유지한다.
- 브라우저 안에서 툴팁을 분리한다. 색 테두리 탐지 실패 시 명암 경계와 짧은 설명창을 검사한다. 여러 창이 있으면 장비 분류·요구 조건을 확인하며, 실제 장비 두 개가 모두 보이면 사용자가 영역을 고른다.
- 자동 선택한 테두리 제외 영역과 그 원본 프레임의 관계를 보존한다. 선택 영역이 구조 검사를 통과하면 같은 원본 프레임을 다시 읽어 별도 장비로 세지 않는다. 선택 영역이 불완전하면 원본 프레임도 검사하고, 별도 프레임은 계속 검사한다. 서로 다른 판독의 숫자 차이를 병합하거나 다수결로 지우지 않는다.
- 반투명 남색 경계의 일부 RGB 채널이 0이어도 대비·닫힌 외곽을 검사한다. 뒤에 비치는 인벤토리의 겹치는 내부 선만으로 실제 외곽을 여러 창의 합성으로 제거하지 않는다. 실제 가로 틈으로 나뉜 두 창과 모호한 후보의 차단은 유지한다.
- 큰 이미지는 작업자에서 전처리하고, CPU·메모리·파일 크기에 따라 1~3장씩 OCR한다. 한 사진의 실패로 다른 사진을 중단하지 않는다.
- 기본 PaddleOCR는 대비 보정한 두 배율의 이미지를 읽고 정규화한 줄 위치를 대응시킨다. 같은 이미지를 그대로 두 번 실행해 일치 표를 만들지 않는다. 반복 잠재 옵션은 실제 줄 개수만큼 유지한다. 숫자·퍼센트가 충돌하거나 한 번만 읽힌 전투 옵션은 확인 대상으로 남긴다.
- 과거 능력창 숫자 영역 전처리(D-097)는 현재 사용자 등록 화면에서 사용하지 않는다. 해당 모듈과 두 배율/순수+추가 관계 검증은 회귀 비교용으로 보존한다. 현재 장비의 요구 조건 재인식은 아래 별도 기준을 따른다.
- 줄 대응은 세로 위치와 가로 겹침을 함께 검사한다. 같은 높이의 다른 위치에 있는 배경 글자를 옵션과 짝짓지 않는다. 옵션 이름만 읽히고 숫자가 사라진 줄도 검토 대상으로 남긴다.
- 기본 경로는 D-150의 미해결 요구 레벨·지원 부스탯·전투 옵션을 최대12줄·줄당8보기 재시도한다. 같은 행의 분리된 숫자와 값 열을 포함하되 다른 필드·다음 행은 넘지 않는다. 회색 명암 보존3배/4배, 휘도 보존3배/4배, 원본 색상3배/4배, 약한 대비3배/4배를 읽고 두 실제 판독의 항목·숫자·% 일치 시 종료한다. 초기 숫자/% 충돌은 다수결로 지우지 않으며 이미 일치한 요구치·전투 옵션은 재시도 대상에서 제외한다.
- 개발·시험에서만 `experimentalRequirementRecovery: true`를 명시하면 요구치(LEV/STR/DEX)를 처음부터 일치한 값까지 원본 색상2배/3배·휘도 보존2배/3배로 별도 검사한다. 기존0~9999 범위·동일 출처/행·숫자 전원 일치·모호한 조각 차단과 초기 근거 보존을 구현했지만 실제 모델 반례에 대한 충분한 승인 조건은 아니다. 이 실험에서만 요구치를 기존8보기 재시도에서 제외하며 두 경로에 중복 투입하지 않는다. 일반 팩토리·단일·일괄·구매 후보 화면은 옵션을 설정하지 않는다.
- 요구치 검증 보기의16px 인공 테두리와 원본 crop을 구분해 기록한다. DB 검출 polygon은 글자 획보다 넓어 빈 테두리까지 확장될 수 있으므로 원시 좌표를 임의로 자르지 않는다. 실제 렌더 끝단과 내용 영역 중심/과반 겹침·같은 행 대응을 검사하며 원본 경계에서 잘린 행과 다른 필드·행은 차단한다. 좌표 검증만으로 픽셀 정보의 완전성을 보장하지 않는다.
- 색상 보정으로 장비명이 사라진 경우 요구치 위 원본 영역을3배/2배로 추가 인식한다. 등급 또는 잠재능력 설정 불가 표식 바로 앞의 이름과 표식이 두 판독에서 일치할 때만 헤더를 복구한다. 날짜·요구 조건·배경 문구를 이름으로 추측하지 않고 이 영역의 숫자는 옵션 합계에 반영하지 않는다. 원본과 헤더 판독은 임시 검토 상태에만 보존한다.
- 수치 필드의 콜론 뒤는 숫자라는 사용자 지적에 따라, 식별된 요구 조건과 알려진 수치 옵션의 `:`/`;` 뒤 값 영역을 숫자로 해석한다. `O→0`, `B→8`을 정규화해 `REQ LEV:BO`와 `REQ LEV:8O`를80으로, `STR:00`·`STR:OO`를0으로 해석한다. `+`가 빠졌어도 알려진 수치 옵션과 콜론이 있으면 읽는다. 원래 텍스트·좌표·퍼센트 단위는 보존하며 두 판독의 일치가 필요하고 숫자 충돌은 유지한다. `IO`·`Q` 등 검증하지 않은 문자를 숫자로 만들거나 빈칸을0으로 채우지 않는다. 보공·총데미지·방무의 누락된%도 추측하지 않는다.
- 콜론 자체만으로 필드를 결정하지 않는다. 같은 줄에서 분리된 `REQ`와 `STR:80`은 가로·세로 좌표로 먼저 결합한다. 장비 분류보다 위에서 읽힌 수치가 요구 조건인지 보너스 옵션인지 불명확하면 확인 대상으로 남겨 잘못 합산하지 않는다. 장비분류·공격속도 등 문자 필드는 숫자로 강제 변환하지 않는다.
- 정상 후보와 검토 입력에는 정규화한 숫자를 표시한다. 요구 조건도 `REQ STR : 0`처럼 제시하며 `O`·`BO` 원문을 후보 버튼으로 내보내지 않는다. 숫자로 해석할 수 없는 값은 입력에서 비워 두고 확인을 막는다. 사용자가 검토 입력에 영문 값을 넣어도 확정하지 않으며, 원래 판독 문자열은 접힌 `인식 원문`에서 읽기 전용으로 보존한다. 현재 숫자 제약은 OCR 이후 해석·검증 단계에 적용되며, OCR 모델 자체의 출력 문자를 제한하는 구현과는 구분한다.
- 추가 인식이 실패해도 기본 인식과 검토 목록을 보존한다. 취소·직업/목적지 변경 시 늦은 추가 결과를 적용하지 않는다. 실험 경로의 검증 실패는 미해결로 남기며 자동 검증에 사람의 확인 상태를 사용하지 않는다. 실험 근거가 있는 항목의 검토 편집·제외 또는 단일/일괄 숫자 입력으로 값을 바꾸면 해당 근거를 무효화한다. 기존 기본 검토·다른 필드·명시적인 사용자 입력은 보존한다.
- 큰 설명창 옆의 작은 정사각형 퀵슬롯은 후보에서 억제하되, 폭이 비슷한 짧은 설명창은 유지한다. 앞의 점·밑줄·콜론 같은 기호와 요구 조건의 LEW/STA 등의 라벨·반복 구분자는 정리하지만 숫자나 누락된 %를 추측해 바꾸지 않는다. 요구 조건 탐지와 숫자 파서는 같은 라벨 정의를 사용한다.
- 옵션 이름이 한 글자 다르게 읽힌 경우 유일한 항목 후보를 재인식 대상 식별에 사용할 수 있다. 후보 문자열만으로 자동 수정하지 않고 해당 원본 영역의 실제 판독이 두 번 일치해야 복구한다. 원래 오독은 근거로 보존하지만 올바른 항목의 일치 횟수로 세지 않는다. 자동 복구가 실패하면 기존 확인 경로와 품질 실패 기록을 유지한다.
- 확인 대상에는 해당 원본 줄, 읽힌 후보, 수정 입력을 표시한다. 큰 고정 스탯은 양쪽 인식이 같아도 추가 확인한다. 미인식은 0이 아니며, 적용 시 기존 값이 유지된다.
- 영역 선택, 대비 보정, 새 사진 선택은 해당 사진만 다시 처리한다. 전체 인식 취소도 완료된 결과와 수정 내용을 남긴다.
- 화면 끝에 닿거나 문자 위치를 읽지 못한 경우 원본의 포함 범위를 추가 확인한다. 재촬영이 필요한 정보는 숫자를 추측해 채우지 않는다.
- 반지는 최대 4개를 착용할 수 있으므로 서로 다른 사진의 이름·옵션이 같아도 기본 포함하고 반지 1~4의 빈 칸에 선택 순서대로 배정한다. 동일 이미지 파일의 재입력은 계속 경고·기본 제외한다. 빈 칸이 없으면 교체할 반지를 선택하거나 사진을 제외하며 다섯 번째 반지를 자동 추가하지 않는다.

## 게임 폰트별 검증

2026-09-27 사용자 확인에 따르면 게임에서 선택 가능한 폰트는 **Noto Sans, 굴림(Gulim)** 두 종류다. 웹앱 UI 폰트 변경 요청은 아니다.

- 각 원본에 게임 폰트 설정을 기록한다. 설정이 확인되지 않은 사진은 `미확인`으로 두며 외형만 보고 확정하지 않는다. `0927_equipment`의 19장은 사용자가 **Noto Sans 설정**으로 촬영했다고 확인했다. 현재 해당 사진의 진단 결과는 Noto Sans 사용 환경의 결과이며 굴림 환경 검증으로 확대하지 않는다.
- 두 폰트별로 요구 레벨·요구 스탯, 장비명, 기본 옵션, 잠재 옵션을 따로 평가한다. 폰트 설정이 요구 조건의 영문·숫자에도 적용되는지 같은 장비의 설정 전후 사진으로 확인한다.
- 각 폰트에서 배율·글자 크기·압축·투명 배경을 바꿔 검증한다. 두 폰트라는 사실만으로 모든 렌더링 형태가 같다고 가정하지 않는다.
- 폰트별 실제 사진과 합성 글자 시험을 구분한다. 설치된 폰트로 만든 숫자 표본은 실제 게임의 획·그림자·크기·배경을 재현했다고 볼 수 없다.
- `0/O`, `8/B`, `1/I`, `%`와 요구 조건 라벨을 집중 검사한다. 폰트 정보는 전처리·재인식 후보를 제한하는 근거이며 숫자 정답 치환표로 사용하지 않는다.
- 인식 개선은 두 폰트에서 잘못된 무확인 채택, 미인식 누락, 불필요한 확인, 처리시간을 함께 비교한다. 특정 폰트 지원 완료는 실제 해당 설정 사진의 검증 후 기록한다.

## 정확도 평가

1. 개인 사진은 `output/ocr-validation/fixtures` 같은 Git 무시 경로에 복사해 고정한다. 원본 폴더가 바뀌어도 전후 비교 자료가 변하지 않아야 한다.
2. 눈으로 읽을 수 있는 부위·기본 옵션·잠재 옵션을 정답표로 만든다. 보이지 않는 값은 추정하지 않는다. 정답표는 평가에만 쓰고 OCR 런타임에서 참조하지 않는다.
3. 개발에 사용한 사례와 별도 검증 사례를 구분한다. 새 사용자 사진이 없으면 위치 이동·크기 변경·JPEG 압축 파생 사례를 사용할 수 있지만, 이를 독립적인 사용자 환경 검증으로 표현하지 않는다.
4. 장비 단위 무수정 완전 인식률(필요 정보 전체가 정확하고 OCR 오류 수동 보정0회), 잘못된 자동 확정, 누락, 수동 수정 횟수, 영역 탐지/처리 실패, 재촬영·영역 재지정, 전체 처리시간을 따로 기록한다. 전체 입력 장수를 보존하고 실패 사진을 성공률 분모에서 제외하지 않는다. 문자별 평균 정확도나 '처리 완료'만으로 장비 정확도100%를 보고하지 않는다.
5. 잘못된 값을 확인 없이 적용할 수 있는 사례는 출시 차단 대상으로 취급한다. 새로운 사진 전체에 오류가 없다고 보장하는 뜻은 아니다.

단위 테스트는 줄 위치 대응, %/고정값 충돌, 옵션 누락, 분리된 라벨/값, 반복 잠재, 저장값 보존, 취소·재시도·늦은 결과를 검증한다. 실제 브라우저에서는 이미지 디코딩, OCR 모델, 작업자, 화면, 저장 전 차단을 함께 확인한다.

## 현재 한계

작은 픽셀 글자, 배경 채팅, 심한 축소·압축은 정보 자체를 손상시킬 수 있다. 두 인식이 같다는 사실만으로 정확성이 증명되지는 않는다. 현재 검토·수정 경로는 잘못된 저장을 막는 안전장치이며, 사용자 보정이 필요한 경우 D-148 목표를 달성하지 못한 것으로 기록한다. 자동 복구를 개선하고 새 캡처 환경을 별도 검증 자료에 추가한다. 현행 브라우저 내부 OCR·외부 전송 금지 정책은 유지한다.

현재 장비 기본은 [PaddleOCR JavaScript SDK](https://github.com/PaddlePaddle/PaddleOCR/tree/main/paddleocr-js)의 한국어 모델이며, Tesseract 어댑터도 회귀 비교용으로 유지한다. 두 엔진 모두 외부 OCR·LLM에 이미지를 전송하지 않는다. 모델·런타임 버전과 라이선스는 [로컬 자산 안내](../public/ocr/paddle/README.md)에 기록한다. Tesseract 비교 시에는 [공식 전처리 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)를 참고한다.

개발 서버와 빌드 결과 양쪽에서 실제 Worker·모델 로딩을 확인한다. 모델·WASM 약 43.4MB 외에 JavaScript 런타임도 필요하므로 첫 방문 다운로드, 브라우저 캐시, 저사양 기기의 병렬 메모리는 별도 측정한다. 숫자 정확도와 최초 로딩 비용을 혼동하지 않는다.

## 개발 후속: 설명창 외곽 선택 보완 — D-ARAN-025

사용자 제공 한 장의 순수 픽셀/사각형 진단에서 실제 툴팁 후보가 있어도 밝은 중성 아이콘 영역만 찾는 선택 규칙이 인벤토리의 흰 격자를 유일한 아이콘으로 골랐다. 좌표 변환/확대의 오차가 아닌 후보 선택 오류였다. 개발 코드에서 본문의 어두운 연속 밴드와 희박한 밝은 텍스트행 근거를 함께 검사하고, 유일한 사각형에도 같은 기준을 적용한다. 아이콘 보조 규칙은 일반적인 유색 내용도 허용하며 strict 후보가 있다는 이유로 flexible 후보를 생략하지 않는다. 불확실한 복수 후보/수동 영역 선택/경고는 보존한다.

동일 한 장에서 기존 인벤토리 선택이 설명창 외곽으로 바뀐 사각형 결과를 확인했다. 이는 명시적으로 요청된 이미지 검토 재현이며 OCR 모델 실행·브라우저 전처리·전체 회귀 QA나 일반 정확도 합격이 아니다. 사용자 직접 QA 지침으로 추가 데이터/테스트/빌드 QA와 운영 배포는 하지 않았다. 개인 이미지·좌표 보고서는 Git제외 output/aran-real-validation/tooltip-border-review/에만 보존한다.

## 개발 후속: 다른 사진 인식 중 개별 영역 선택 — D-ARAN-026

다중 인식의 전역 busy 값이 완료된 다른 사진의 영역 선택과 재시도까지 막던 경로를 행별 상태로 분리했다. 완료/실패 행은 영역 선택·확인이 가능하며 같은 행의 대기/재인식/적용 중에는 중복 작업을 막는다. 확인한 영역은 해당 행에 보존하고 기존 초기 OCR 풀 워커가 현재 사진을 마친 다음 우선 재시도한다. 풀 종료 경계에 도착한 요청은 직렬 드레인으로 처리하여 요청 유실/추가 병렬 모델을 피한다.

원본 파일·시도 번호·작업 identity/abort를 확인하는 functional update로 늦은 결과를 차단한다. 다른 행 진행으로 열린 영역 선택기를 다시 만들지 않고 같은 사진/분류 재시도는 사용자가 정한 적용 부위/이름/펜던트 선택을 유지한다. 작업 중 해당 행 편집은 잠그고 전체 취소는 queued 영역/다른 완료 결과를 보존한다. borrowed 초기 워커는 풀에서 정리하고 개별 소유 워커만 재시도에서 정리한다. 전체 적용·저장은 처리 및 원본 검토가 끝나야 한다.

이는 소스 설계/구현 기록이다. 사용자 직접 QA 지침으로 OCR·브라우저·테스트·타입·린트·빌드 QA는 실행하지 않았고 운영에는 배포하지 않았다.
