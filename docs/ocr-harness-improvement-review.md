# 기존 실험에서 찾은 OCR 하네스 개선점

2026-10-11 · 조사 결과와 에이전트 제안 · 구현 승인/성능 개선 완료와 구분

현재 하네스는 잘못된 후보의 제품 적용을 막고 결과를 보존하는 역할을 수행했다.
다음 개선의 핵심은 **실패한 실험을 다음 실험의 입력으로 연결하는 것**이다.
학습을 더 오래 돌리기 전에 자료 재사용 계약, 전처리 비교, 후보 선택과 부분 결과 저장을
정비하는 순서를 권한다. 이번 작업에서는 학습·추론·하네스 코드를 변경하지 않았다.

## 조사 범위와 실제 근거

OCR 구현은 `C:/Autoresearch-experiments/task132/Autoresearch-task132`의
`feat/132-ocr-research-harness` 작업 트리에 있다. 신규 OCR 소스는 미커밋 상태이며
기준 HEAD `f06c9ab`만으로 해당 구현을 재현했다고 표현할 수 없다.

### H-01: 가장 먼저 풀어야 할 자료 사용 문제

`ocr_exposure.py`의 `expose()`는 노출 DB의 이전 role이 `final`이면
`ocr_previously_final_exposure`로 거절한다. 새 final 재사용을 막는 목적은 필요하지만,
현재 계약에서는 이미 소비된 사진으로 다음 개발/진단 실험을 하는 경로도 막힌다.
이 때문에 후속 31장을 개선용으로 사용한다는 계획에는 별도 계약이 필요하다.

개인 자료 없는 synthetic CPU probe에서 final claim 1건을 만든 뒤 같은 source/crop을
diagnostic으로 등록했을 때 거절을 재현했고 claim은 1건으로 유지됐다.
제안은 DB 삭제·새 DB 생성·source 해시 변경으로 우회하는 것이 아니다.
소비 이력을 보존하는 명시적 역할 전환과, 이후 모든 fresh final에서의 거절을 함께 구현한다.
이 기능을 추가해도 이번 31장은 새 최종시험 자료가 될 수 없다.

### H-02: 경계·배경 실험을 하네스 안으로 넣기

`ocr_domain.py`의 `validate_candidate()`는 prediction의 crop hash와 추출 실패 상태가
snapshot과 같은지 검사한다. `evaluate()`는 baseline에도 동일 검사를 적용한다.
이 무결성 검사는 유지해야 한다. 다만 서로 다른 경계·마스크 입력을 한 snapshot에
넣으면 정상적인 전처리 차이도 hash mismatch로 거절된다.
synthetic CPU probe에서도 다른 crop의 거절을 재현했다.

따라서 P0/P1/P2마다 파생 snapshot을 만들고 각 입력의 원출력을 독립 채점한 뒤,
별도 비교기가 공통 원본/행/필드/정답의 대응을 확인해 개선·회귀를 계산해야 한다.
baseline crop hash를 후보 값으로 덮어써 검사를 통과시키면 안 된다.
전처리 때문에 영역 추출 성공/실패가 바뀌는 경우도 같은 전체 대상 분모에서 비교한다.

실행기는 경계 좌표·마스크·전처리 설정과 코드 hash·고정 모델·원출력을 묶어 저장한다.
획 손실과 배경 잔존은 정답 문자열만으로 분리할 수 없으므로, 일부 검수된 원본 행에
전경/경계 annotation과 희미한 숫자 회귀 사례를 갖추고 별도 측정해야 한다.
이 adapter/비교기/픽셀 검증은 현재 완료 기능이 아니다.
[기존 BG-0~6 계획](ocr-accuracy-improvement-plan.md#숫자-영역-경계배경-억제-개선-계획--2026-10-11)과 연결한다.

### H-03·05: 좋은 validation 점수와 안전한 후보를 구분하기

`ocr_controller.py`는 epoch에서 `metrics.exact > best.metrics.exact`, trial 사이에서는
`max(..., key=metrics.exact)`로 선택한다. 숫자 오답은 ledger에 기록하고
최종 Judge도 검사하지만, 선택 시 숫자 오답·회귀의 적격 조건은 없다.
동률이면 먼저 관측한 후보가 남는다. 안전한 동점 후보가 뒤에 있어도 선택 기준이
그 차이를 사용하지 않는 구조다.

제안하는 순서는 사전 고정 위험 조건 충족 여부 → 적격 후보끼리 원문 exact →
동점 규칙이다. 미달 후보도 진단 결과로 보존하되 단일 final을 소비할 대상으로
자동 승격하지 않는다. 모든 후보가 미달이면 후보 없음으로 종료한다.
최종 99%·숫자 오답0·회귀0 기준은 결과를 본 뒤 완화하지 않는다.

다만 선택 규칙만으로 새 사진의 오류를 해결할 수는 없다. 실제 M132는 세 epoch 모두
validation 38/38이었고, 이 자료는 LEV/STR만 포함했다. 이후 다섯 필드·새 배경의
후속 시험에서 위험 오류가 드러났다. 전처리 실험은 이미 관찰된 31장을 개발 challenge로
사용할 수 있지만, 학습 실험에서 반복 선택에 사용할 자료와 별도 진단 자료의 역할은
실험 시작 전에 정해야 한다. fresh final은 다른 장비/촬영 조건의 새 원본으로 분리한다.

coverage 항목에는 LEV/STR/DEX/INT/LUK, 흰색/빨간색, 밝은/어두운 배경,
희미한 획, 0/비0, 각 숫자, 촬영 세션/배율/장비 그룹과 unknown을 포함한다.
현재 후속 시험의 숫자9는 미검증이다. 표본이 작거나 한 촬영 그룹뿐인 결과는 그대로
표시하고, 반복 seed가 같은 촬영 조건의 부족을 해결한다고 주장하지 않는다.

### H-04: 중단되어도 완료한 관측을 잃지 않기

현재 자동 진단 helper는 `auto-browser.ts`를 재사용했다. `onResult`에서
결과를 `outputs` 배열에 쌓고, 모든 사진이 끝난 뒤에 pipeline을 저장한다.
진행률은 전송하지만 각 사진의 판독·영역 산출물은 먼저 게시하지 않는다.
실제 600초 진단에서는 마지막 10/31 진행 상태만 관측했고 채점할 완결 영수증을 얻지 못했다.
이를 155개 OCR 실패로 집계하면 안 된다.

사진별 임시 결과를 서버가 원자적으로 게시하고 hash가 붙은 완료 receipt를 돌려주는
계약을 추가한다. 전체 집계는 원래 목표 필드 목록과 연결해 만들고, interrupted run의
부분 관측은 완결 정확도와 별도로 표시한다. timeout은 runtime 실패이며
TOOLTIP_NOT_FOUND 같은 실제 추출 실패와 구분한다.

학습/validation/diagnostic의 완료 작업은 영수증 검증 후 재개할 수 있다.
final의 부분 게시·재개는 별도 소비 계약이 필요하며 기존 claim을 초기화하지 않는다.
현재 `ocr_stage_ambiguous`는 불명확한 작업의 자동 중복을 막는 장치다.
이 거절을 제거하는 대신, 부분 영수증으로 무엇이 완료됐는지 더 명확하게 만든다.

### H-06~08: 다음 실험의 선택과 실행 비용 줄이기

CTR에는 `feedback.py`의 `FeedbackPayload`, `build_feedback()`가 있으며 과거 #63에서
첫 trial feedback을 받은 후 다음 후보를 실행했다. OCR Controller는 `ExperimentCard`를
공유하지만 이 feedback 경로를 호출하지 않는다. 설정 목록을 사람이 미리 제공한다.
따라서 프로젝트 전체의 feedback 부재가 아니라 **OCR 연결의 공백**이다.

첫 단계는 LLM 코드 생성보다 로컬의 구조화된 오류 보고와 제한된 가설 카드를 권한다.
예를 들어 배경 혼입·획 손실·추출 누락·변환 불일치·실행 실패를 구분하고,
각 가설이 바꾸는 요소 하나와 검증할 반례를 명시한다. 최종시험 결과를 본 다음
다시 선택하는 경우에는 새 개발 연구와 새 final이 필요함을 기록한다.
전처리로 줄일 수 있는 오류와 학습으로 줄일 오류를 동일 trial에서 섞지 않는다.

`_report()`에는 validation/final 점수가 있지만 CLI `run`은 status·selected_epoch·
validation만 출력한다. final의 오답/회귀와 실패 단계 경로, partial 상태를 함께
표시하면 결과를 확인하는 수동 작업을 줄일 수 있다. runtime 실패 receipt의
`runtime_operation_failed`에는 구체적인 bounded 원인 코드와 private 상세 로그 참조를
연결한다. 개인 원문·사진은 공개 로그/feedback에 노출하지 않는다.

후속 A1 baseline은 역사적 모델 identity와 실제 runtime identity를 별도 attestation으로
연결했다. 원출력 변조는 없었지만 다음 실험부터는 이를 versioned baseline 스키마의
별도 모델/환경 필드로 표현하면 수동 연결과 해석 혼동을 줄일 수 있다.

실제 연속 epoch RNG 문제와 Windows Temp 경로 문제는 이번 OCR 작업에서 이미 보완했다.
CTR #118에서도 supervisor 호출 인자와 CRLF byte pin 문제가 실행 준비에서 관측됐다.
이런 경험은 환경 점검·실제 연속 호출 smoke·짧은 시험 경로를 미리 제공하는 근거다.
환경 pin이나 판정 기준을 느슨하게 하는 개선을 제안하는 것은 아니다.

## 권장 진행 순서와 보존할 기능

1. H-01·02: 소비 자료의 개발 역할 전환과 입력안 비교 계약을 먼저 정의한다.
2. H-03·05: 선택 적격 조건과 coverage를 고정한다. 이미 본 사진은 개발용으로 표시한다.
3. H-04·06: 사진별 저장·재개·실패 분류·가설 카드를 연결한다.
4. H-07·08: identity 이관과 환경 preflight를 정비한다.
5. 고정 M132로 P0/P1/P2를 먼저 비교하고 이후 필요한 경우 별도 학습 연구를 진행한다.

그대로 보존할 기능은 독립 raw Judge, 전체 필드 분모, 원출력/해시 봉인,
train 정답과 평가 입력의 분리, 단일 final claim, GPU/ONNX/browser 원문 동등성 검사,
소유 프로세스 cleanup과 완료 artifact 재검증이다. 실제 완료 재호출은 runtime 추가0회·
177파일 불변이었으므로 재개 엔진 전체를 새로 쓰는 것보다 위 공백을 추가하는 편이 타당하다.
