# 검증된 OCR 복구 결과의 자동 통과 구현 계획

상태: 구현 제안. 사용자 요청은 계획 수립이며, 이 문서 작성으로 판정 규칙 변경·구현·운영 배포를 실행하지 않는다. 확정 정책과 결정 이력은 AGENTS.md 및 DECISIONS.md를 따른다.

## 1. 목표와 첫 적용 범위

사용자가 OCR 오류를 고치지 않아도, 시스템이 원본을 다시 읽어 검증 조건을 충족한 값을 자동 채택한다. 초기 판독의 실수가 이후 검증 성공을 영구적으로 막지 않도록 한다.

- 1차 대상: 요구 레벨과 현재 지원 직업의 요구 부스탯. 기존 `JOB_RULES`에서 사용하는 LEV/STR/DEX 집합을 재사용해 캡틴 외 기존 동작도 보존한다.
- 전투 옵션의 숫자/% 충돌, 큰 고정 스탯, 미확인 옵션은 이번 요구치 예외로 통과시키지 않는다. 전투 옵션까지 같은 정책을 확장하려면 퍼센트·반복 잠재·합산 검증을 별도 수행한다.
- 현재처럼 검토가 필요한 줄만 재시도하면 두 초기 판독이 같은 오답을 낸 경우를 놓친다. 요구치 전용 검증은 발견된 대상 필드 전체에 적용한다. 요구치가 아예 검출되지 않으면 값을 만들어내지 않는다.
- 장비 한 개의 전체 성공과 요구치 한 줄의 복구 성공을 구분한다. 다른 필드의 미해결 문제와 사진 범위 경고는 그대로 남긴다.
- 브라우저 내부 모델·기존 계산식·저장 형식을 유지한다. 확인/저장 버튼 제거와 무조건 자동 저장은 범위에 포함하지 않는다.

## 2. 현재 문제가 생기는 지점

`recognizePaddle.client.ts`는 강한 보정의 전체 판독을 두 번 수행한다. `retryRecognition.ts`는 추가 판독을 같은 `readings`에 누적하고 `buildOcrReview`를 다시 호출한다. `reviewRecognition.ts`는 서로 다른 숫자가 하나라도 있으면 차단한다.

D-152의 세 사진 실험에서는 원본 색상과 휘도 보존의 요구치 줄 판독이 각각6/6 일치했다. 초기 오독과 후속 검증을 구분하는 자료 구조 및 최종 채택 절차가 현재 없다. 다만 이 결과는 알려진 세 사진의 근거이며 모든 사진에서 해당 방법이 맞는다는 증명은 아니다.

## 3. 판독과 최종값을 분리한다

다음 정보를 임시 인식 상태에 추가한다. 이미지와 판독 원문은 서버나 브라우저 영구 저장에 넣지 않는다.

| 정보 | 역할 |
|---|---|
| 판독 출처 | `discovery` 전체 탐색, `verification` 원본 영역 검증, 정보가 없는 기존 판독은 `legacy`로 구분 |
| 이미지/작업 식별자 | 다른 이미지·취소된 작업·재선택 전 결과의 재사용 방지 |
| 필드·원본 좌표 | 요구 항목과 동일 줄의 숫자를 검증했는지 확인 |
| 보기 정보 | 원본 색상/휘도 보존, 배율, crop 영역, 판독 식별자 |
| 최종 복구 결과 | 채택값, 검증에 사용한 판독, 대체된 탐색 판독, 이유와 규칙 버전 |

기존 `pass` 숫자만으로 탐색/검증 단계를 추정하지 않는다. 동일 판독을 복제해 근거 수를 늘릴 수 없도록 보기와 작업 식별자를 확인한다. 기존 메타데이터 없는 리뷰에는 자동 예외를 소급 적용하지 않는다.

초기 오독은 삭제하지 않는다. 원문은 추적용으로 보존하고, 요구치의 최종값은 전용 검증 결과에서 얻는다. 검증 성공 시 탐색값을 대체한 사실을 명시하며 단순히 `readings`에서 불리한 값만 제거하지 않는다.

## 4. 원본에서 검증용 영역을 만든다

`retryRecognitionBounds`와 `requirementView`를 활용하되 다음 조건을 검사한다.

1. 항목명과 요구치의 위치가 식별돼야 한다. 숫자가 읽혔다는 이유만으로 STR 보너스 옵션을 요구 STR로 바꾸지 않는다.
2. 항목명·구분자·값 전체를 포함한다. 기본 경계 여백은 원본 기준2px를 시작값으로 시험하고, 이 수치는 반례 실험으로 조정한 뒤 고정한다. 장비명/파일명별 좌표는 사용하지 않는다.
3. 위아래 인접 행의 중간선과 오른쪽의 다른 필드를 넘지 않는다. 검출된 글자 상자가 영역 끝에 걸리거나 원본 이미지 경계 때문에 여백을 확보하지 못하면 불완전 영역으로 분류한다.
4. 각 검증 보기의 검출 좌표를 원본 좌표로 환산해 동일 행·값 열에 대응하는지 확인한다. 라벨과 숫자가 분리 검출되면 이 좌표 조건을 충족하는 조각만 결합한다.
5. 값이 두 개이거나 다른 요구 항목이 함께 들어오면 임의로 하나를 고르지 않는다. 큰 crop 전체의 텍스트를 무조건 이어 붙이지 않는다.
6. 동일한 요구 필드가 서로 다른 두 행에 발견되면 어느 행이 맞는지 임의 선택하지 않는다. 같은 행을 여러 배율에서 발견한 경우만 하나의 대상으로 묶는다.

위치 정보만으로 픽셀의 의미가 완전히 증명되지는 않는다. 기존 사진 끝 경고를 해제하지 않고, 자르기 경계의 판정은 잘린 숫자·두 열·인접 행 반례로 검증한다.

## 5. 고정된 검증 보기와 자동 통과 조건

요구치 줄은 강한 흰색 추출 보정을 거치지 않은 원본에서 다음 네 보기를 만든다.

- 원본 색상2배·3배
- 휘도 보존2배·3배

같은 Paddle 작업자를 재사용한다. 네 보기를 모두 평가해 마지막 보기의 충돌을 놓치지 않는다. 최대 세 대상 필드이면 기본 상한은12회이며, 같은 보기의 반복 실행이나 충돌 후 무제한 재시도는 하지 않는다. 중단/실패도 결과에 남긴다.

### 자동 통과에는 아래 조건이 모두 필요하다

| 조건 | 판정 |
|---|---|
| 동일 원본·작업·필드·행 | 모두 일치하고 crop이 완전해야 함 |
| 변환 종류 | 원본 색상과 휘도 보존에서 각각 최소1개 유효 판독 필요 |
| 배율 | 유효 판독에2배와3배가 모두 포함돼야 함 |
| 필드와 형식 | 요구 라벨과 비음수 정수 전체가 식별돼야 함. 기존 범위 검사 유지 |
| 값 일치 | 유효한 검증 판독 전부의 값이 동일해야 함 |
| 모호한 조각 | 같은 값 열에 다른 숫자 후보가 남으면 통과하지 않음 |
| 작업 상태 | 취소·이미지 교체·목적지 변경 이전의 결과는 적용하지 않음 |

기존의 제한된O→0·B→8 정규화는 재사용한다. 빈칸·Q·I·누락된%를 추측해 숫자로 만들지 않는다. 읽지 못한 결과는 동의표로 세지 않으며, 형식이 불완전하다는 이유로 같은 값 열의 다른 숫자 증거를 숨기지 않는다.

이 조건은 다수결이 아니다. 예를 들어 유효 결과가 세 번 같은 값이고 한 번 다른 값이면 차단한다. 두 방식·두 배율의 근거를 충족하고 다른 유효 값이 없는 경우만 자동 채택한다. 어느 한 방식만 반복해서 같은 값이 나와도 통과하지 않는다. 엔진 신뢰도 점수는 진단 자료로 보존하며 점수 하나로 통과시키지 않는다.

같은 모델의 다른 변환은 독립적인 정답 판정자가 아니다. `verified`는 이 검증 규칙을 통과했다는 의미이며, 실제 정답률은 별도 사진·반례 시험으로 확인한다.

### 탐색값과 충돌할 때

- 요구치의 전용 검증이 통과하면 해당 값이 최종값이다. 전체 탐색의 숫자와 달라도 `initial-reading-superseded` 사유와 기존 원문을 보존한다.
- 전용 검증끼리 충돌하거나 영역 검증이 실패하면 `unresolved`다. 같은 값을 더 많이 읽어 해결하지 않는다.
- 전용 검증을 끝내지 못했는데 초기 두 판독이 같다는 이유로 새 자동 통과를 부여하지 않는다.
- 요구치 이외의 줄에는 이 예외를 적용하지 않는다. 기존 전투 옵션 충돌 검사와 중복 합산 방지는 유지한다.

## 6. 모듈과 연결 순서

최종 판정은 DOM·저장·모델 실행에 의존하지 않는 `verifyRequirementRecovery.ts` 모듈에 모은다. 작은 인터페이스로 위치/판독 자료를 받아 `verified` 또는 사유가 있는 `unresolved`를 반환한다. 호출자가 점수와 충돌 예외를 따로 조합하지 않도록 한다.

```ts
verifyRequirementRecovery(locatedRequirement, observations): RecoveryDecision
```

| 순서 | 파일 | 변경 목적 |
|---|---|---|
|1|`ocr/types.ts`|판독 출처·원본 좌표·보기 식별자·복구 결과를 임시 자료 구조로 추가|
|2|`ocr/retryRecognition.ts`, `requirementView.client.ts`|검증 영역 준비와 원본 색상/휘도 보존 보기 생성, 원본 좌표 대응|
|3|`ocr/verifyRequirementRecovery.ts` 신규|동일 필드·위치·보기 다양성·숫자 일치·불완전 증거 판정|
|4|`ocr/recognizePaddle.client.ts`|모든 대상 요구치의 네 보기 실행, 작업자 재사용·취소·횟수 제한·진행률 처리|
|5|`ocr/reviewRecognition.ts`|초기 후보와 검증된 최종값을 구분해 리뷰/적용값 생성|
|6|기존 단일/일괄/후보 입력|같은 최종 리뷰 결과를 소비하는지 통합 검증|

1차는 `OcrReviewLine`에 선택적인 복구 근거를 추가하고, 자동 복구 성공 시 기존 `recognized` 상태와 정규화된 최종 `text`를 사용한다. 사람이 확인한 `confirmed` 상태로 위장하지 않는다. `mapReviewedStats`·`reviewQuestions`·`reviewBlocked`·`reviewText`가 같은 최종 결과를 따르게 한다.

원시 판독 배열을 다시 `buildOcrReview`에 넣는 경로에서 검증 결과가 유실돼 재차 차단되지 않도록, 최종 리뷰 조립을 한 곳에서 수행한다. 최종값은 존재하는 유효 복구 근거와 함께 생성하고, 원문 편집·이미지/영역 교체 시 근거를 무효화한다. 사람이 명시적으로 수정한 값은 기존 수동 편집 규칙을 유지한다.

`EquipmentOcrPanel`, `EquipmentOcrBatchPanel`, `recognizeBatch.client`에는 판정 규칙을 복제하지 않는다. 인식기의 기존 콜백/반환 계약을 유지하고 같은 리뷰를 전달한다. 브라우저 영구 저장에는 기존 장비 숫자만 저장한다. 원본 확인/저장 버튼은 그대로 두되 복구된 항목의 수동 숫자 수정 요구는 사라져야 한다.

전용 검증으로 옮긴 요구치는 기존8보기 재시도 대상에서 제외한다. 같은 필드를 두 복구 경로에서 반복 판독하거나 오래된 병합 규칙으로 다시 차단하지 않도록 한다. 전투 옵션의 기존 재시도 경로는 유지한다.

## 7. 검증 순서와 합격 기준

### A. 판정 모듈의 반례 테스트

- 잘못된 탐색값 + 조건을 만족한 원본 검증값 → 자동 복구 및 초기 근거 보존.
- 탐색값이 없거나 두 번 동일 오답이어도 검증 결과에 따라 판정.
- 검증값 충돌, 한 변환만 일치, 동일 보기 복제, 서로 다른 이미지/행/필드 → 차단.
- 실제 값이0뿐 아니라1·17·60·80 등인 수치 사례에서 값을 바꾸지 않음. 수치는 합성 판정 시험이며 실제 게임 사진의 정확도 증거로 사용하지 않음.
- 잘린 첫/끝 숫자, 라벨 누락, 다중 값, 요구 STR와보너스 STR 혼동, 소수/음수/퍼센트·빈칸 → 기존 정확성 조건 유지.
- 수동 수정/제외, 취소·늦은 응답·같은 이미지 중복 요청, 재검토, 프리셋/직업 변경 → 잘못된 증거 재사용 없음.

### B. 실제 모델 비교

1. 알려진 원본20장 전후를 같은 환경에서 실행한다. 기존17장 회귀0건과 남은3장 무수정 복구를 목표로 한다.
2. 위치 이동·툴팁 자르기·JPEG·축소 파생4장을 별도로 평가한다. 축소로 여전히 누락되면 실패로 남긴다. 안전하게 차단된 것도 무수정 성공으로 세지 않는다.
3. 개발에 사용하지 않은 실제 사진과 다른 배경·해상도·Noto/Gulim 사례를 별도로 확보해 검증한다. 확보하지 못한 영역은 미검증으로 명시한다.
4. 잘못된 자동 확정이 한 건이라도 생기면 이 판정 조건의 도입을 보류하고 원인을 수정한다. 숫자별 정답 치환이나 실패 사진 제외로 지표를 개선하지 않는다.

평가표에는 전체 원본 수, 장비 단위 필수값 완전 일치+수동 수정0회, 잘못된 자동 확정, 누락/차단, 수동 수정 횟수, 처리시간 중앙값·상위구간, 추가 호출 수를 따로 기록한다. 초기 모델 로딩과 warm 실행을 분리하고 동시 빌드 없이 비교한다. 시간 허용량은 사용자가 확정한 정책이 아니므로 실제 측정치와 정확도 이득을 제시한다.

### C. 앱 통합과 품질 확인

- 단일 장비·일괄 등록·구매 후보에서 동일한 검증값을 표시하고, 숫자 수정 없이 저장/비교가 이어지는지 확인한다.
- 새로고침 후 장비 숫자 복원, 후보/사진 비영구 보관, 기존 세팅 비오염을 확인한다.
- 다른 미해결 옵션과 사진 범위 경고는 계속 보류한다. 사진 전체가 완전한지 검증하지 않은 채 요구치 한 줄 성공을 장비 전체 성공으로 표시하지 않는다.
- 관련 판정/인식/리뷰/저장 회귀, 전체 테스트, 타입·린트, Vinext·Next.js Webpack 빌드 및 실제 브라우저 흐름을 확인한다.

## 8. 실행 단계와 완료 산출물

1. **근거 분리와 판정 모듈:** 자료 구조·순수 판정·반례 테스트를 먼저 구현한다. 이 단계는 앱의 기존 판정을 바꾸지 않는다.
2. **검증 전용 판독 연결:** 실제 모델로 제안한 규칙을 시험하고, 검토 결과를 변경하지 않는 진단 모드에서 기존/신규 결정을 대조한다.
3. **자동 복구 반영:** 기준을 통과한 요구치에만 최종값을 연결하고 단일/일괄/후보 흐름을 확인한다.
4. **회귀·정책 동기화:** 자동 채택 근거와 남은 실패를 보고하고, 구현을 요청받아 실제 규칙이 변경되는 시점에 AGENTS.md·검증 문서·DECISIONS.md를 함께 갱신한다.
5. **작업 브랜치 업로드:** 코드·테스트·관련 문서만 비운영 브랜치에 커밋·푸시한다. 개인 사진/원문은 Git 제외output에 보관한다. 운영 반영은 사용자의 명시적 요청을 따른다.

완료 산출물은 검증된 판정 모듈, 실제 모델/브라우저 결과표, 오답 자동 확정 반례 테스트, 변경된 검토 흐름과 남은 실패 목록이다. 요구치 복구 구현 완료를 서비스 전체의 무수정 목표 달성으로 표현하지 않는다.
