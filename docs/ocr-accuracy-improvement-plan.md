# 장비 사진 판독 정확도 개선 계획

**2026-10-10 최신 평가 기준(D-OCR-CATEGORY-CRITERION-20261010-017): 장비명 일치는 성공 조건에서 제외한다.** 장비 식별은 분류로 판단하고 계산에 필요한 옵션·요구 조건의 정확성과 미해결 검토 여부를 평가한다. 아래 과거의 장비명 포함 결과는 당시 기준의 이력이며 현재 합격 기준으로 사용하지 않는다.

사진을 넣은 뒤 사용자가 항목명·숫자·누락값을 고치지 않아도 장비를 정확히 등록하는 것을 목표로 한다. 현재 문제의 핵심은 미식별 줄이 자동 재인식에 연결되지 않는 점과, 같은 모델이 반복해서 낸 오답을 검증된 값과 구분하기 어려운 점이다. **재인식 대상 확대부터 진행하고, 원본 검증과 장비 전체의 누락 검사를 통과한 결과만 적용한다.**

작성일은 2026-10-01이다. 이 문서는 사용자의 계획 작성 요청에 따른 구현 제안이며, 계획 작성 완료와 정확도 개선 구현 완료를 구분한다. 현재 앱 소스·판정 규칙·개발 서버·운영 버전은 이 문서 작성으로 변경하지 않는다. 확정 정책과 요청 이력은 [AGENTS.md](../AGENTS.md)와 [DECISIONS.md](../DECISIONS.md)를 따른다.

**후속 구현 상태:** 사용자의 구현 시작 요청에 따라 실패 판독 관측과 공통 행 복구 Module을 구현했다. 사용자 확인으로 이번19장은 돋움 자료로 분류했다. 자동 적용 후보와 여러 모델/전처리·돋움 합성 학습 후보를 실제 브라우저에서 비교했으나 무수정 완전 인식 기준을 통과하지 못했다. 제품 기본값에는 새로운 자동 확정 규칙이나 모델을 활성화하지 않았으며 전체 계획과 정확도 목표는 미완료다. 아래의 설계·검증 기준은 계속 적용한다.

## 현재 확인된 문제

사용자가 제공한 개발 자료 19장에서 설명창 후보 오류를 수정한 뒤 실제 브라우저의 로컬 Paddle 인식 호출은 모두 끝났다. 그러나 13장에 확인 필요 16줄이 남았다. 확인 줄이 없는 6장도 전체 옵션을 정답표와 대조하지 않았으므로 완전 인식 성공으로 계산하지 않는다.

| 항목 | 남은 줄 | 현재 실패 원인 | 직접 개선할 부분 |
|---|---:|---|---|
| 올스탯 | 8 | 여러 글자가 잘못 읽혀 알려진 항목으로 식별되지 않음 | 이름 후보 탐색과 실제 원본 재판독 연결 |
| DEX | 3 | 2줄은 첫 글자 오독으로 파서 진입 실패, 1줄은 숫자 충돌 | 미식별 행 재판독과 숫자 검증 |
| 요구 레벨 | 1 | 알려진 요구 항목이지만 정상 숫자로 복구되지 않음 | 실패 판독 기록과 요구치 영역 검증 |
| 방어력과 MP | 4 | 참고 항목 이름을 식별하지 못해 미지원 계산 옵션과 구분되지 않음 | 참고 항목의 의미를 검증한 뒤 적용 차단 여부 결정 |

16줄 중 14줄은 `retryRecognitionLabel`이 항목을 찾지 못해 자동 재인식 대상으로 선택되지 않는다. DEX의 숫자 충돌 1줄에는 받아들인 추가 판독 8개가 있지만, 첫 판독의 다른 숫자를 보존하는 기존 규칙 때문에 차단된다. 요구 레벨 1줄에는 정상 옵션으로 받아들인 추가 판독이 없다. 현재는 실패한 재판독 문자열을 모두 남기지 않으므로 이 기록만으로 실제 시도 횟수나 실패 지점을 확정할 수 없다.

이 결과는 이미 `dev-main`의 구조 개선을 포함한 소스에서 얻었다. `v0.0.0`과 `dev-main`의 모델·전처리·옵션 파서·검토·재인식은 같으며, 같은 판독 자료를 두 버전 규칙에 재생해도 13장·16줄이 동일했다. 새 `batchReview`는 검토·장비 배정·재시도 선택 보존을 공통 Module에 모은 것이다. 문자 정확도 개선은 별도의 작업이다.

관련 진단 자료는 Git 제외 `output/tooltip-candidate-repro/`와 그 아래 `analysis/`에 보존했다. 개인 이미지·정답표·판독 원문·원본 좌표는 공개 문서와 커밋에 포함하지 않는다.

## 목표와 성공 판정

장비 한 개의 성공은 **등록에 필요한 정보 전체가 원본과 일치하고, 인식 오류 보정을 위한 사용자 개입이 0회인 경우**다. 항목명이나 수치를 고친 뒤 등록한 사례, 안전하게 차단된 사례, 확인 경고만 사라진 사례는 성공에 넣지 않는다. 사용자가 등록할 부위·가격·순수 스탯을 선택하거나 마지막 저장 버튼을 누르는 일은 인식 오류 보정과 구분한다.

등록에 필요한 OCR 정보는 실제 화면에 표시된 장비 분류와 해당 직업/장비에 적용할 고정 스탯·스탯%·공격력·공격력%·전투 옵션·요구 조건이다. 반복 잠재 줄의 개수와 고정값/% 단위를 포함한다. 장비명과 등급 표식의 문자열 일치는 필요 정보에서 제외한다(D-OCR-CATEGORY-CRITERION-20261010-017). 없는 항목과 읽지 못한 항목을 구분하며, 미인식을 0으로 채우지 않는다. 참고 항목의 정확한 분류와 수치 판독 상태는 따로 기록한다.

| 지표 | 단계 완료를 판단할 기준 |
|---|---|
| 이번 개발 자료의 무수정 완전 인식 | 19장 전부를 정답표로 채점하며 최종 목표는 19/19 |
| 잘못된 자동 채택 | 개발 자료·회귀 자료·반례·별도 평가 자료 각각 0건 |
| 기존 정상 사진 회귀 | 정답표로 기존 성공을 확인한 장비의 필수 정보·옵션 합계·저장 결과 변화 0건 |
| 누락 탐지 | 사라진 지원 옵션, 마지막 줄 잘림, 빠진 %를 성공으로 통과시키지 않음 |
| 사용자 보정 | 수정·누락값 입력·행 제외·영역 재지정은 0회가 목표이며 발생하면 실패로 기록 |
| 처리 비용 | 초기 모델 준비와 이후 판독을 분리해 시간 중앙값·상위 구간·추가 호출·메모리를 측정 |

19/19와 오채택 0건은 이번 평가 자료에서의 통과 기준이다. 모든 사용자·게임 폰트·해상도의 정확도 보장으로 표현하지 않는다. 독립 사용자의 무개입 등록·저장·후보 비교 POC는 [기존 POC 정의](poc-definition.md)에 따라 별도로 확인한다.

## 과거 실험에서 반영할 제약

[기존 요구치 검증 계획](ocr-verified-recovery-plan.md)은 활성화 기준을 통과하지 못했다. 과거 원본 20장의 기존 기준은 17장 통과였으나 후보 v4는 16장으로 회귀했다. 실제 모델을 사용한 합성 56사례에서는 희미한 숫자의 일부가 사라진 8사례를 잘못 자동 채택했다.

따라서 원본 색상과 휘도 보존 보기에서 같은 값이 나왔다거나 여러 배율의 판독이 일치했다는 사실만으로 정확성을 확정하지 않는다. 같은 모델의 보기들은 상관된 오답을 낼 수 있다. 원본 글자 전체가 남아 있는지, 해당 행과 값 열이 맞는지, 숫자·%가 누락되지 않았는지를 검증해야 한다. 글자의 정보를 잃은 자료는 안전하게 차단하되 성공으로 세지 않는다.

`experimentalRequirementRecovery`는 계속 기본 비활성 상태로 둔다. 기존 실험 코드는 출처·관측·취소 계약을 참고할 수 있지만, 미통과 판정 규칙을 켜거나 이름만 바꿔 일반 판독에 적용하지 않는다.

## 구현 순서

각 단계는 다음 단계가 쓸 수 있는 근거를 만든다. 단계를 마칠 때 목표와 실제 결과를 비교하고 남은 실패를 기록한다. 초기에는 검토 결과를 바꾸지 않는 진단 경로로 실험하고, 검증된 규칙만 최종 리뷰에 연결한다.

| 순서 | 작업 | 완료 조건 | 다음 단계의 입력 |
|---|---|---|---|
| 1 | 정답표와 모든 재판독의 관측 기록 | 19장 필수 필드·반복 옵션을 채점 가능하고 실패한 시도도 추적 가능 | 고정된 평가 자료와 실패 위치 |
| 2 | 미식별 줄을 재인식 대상에 연결 | 현재 16줄 모두 안전한 대상 선택 또는 명시적인 불완전 영역 사유를 반환 | 원본 행과 항목 후보 |
| 3 | 항목명과 참고 항목을 원본에서 식별 | 올스탯·영문 스탯·참고 항목의 오독을 해결하며 모호한 행을 임의 확정하지 않음 | 검증할 필드와 숫자 영역 |
| 4 | 숫자와 % 및 충돌을 검증 | 요구 레벨·DEX 복구와 과거 숫자 손실 반례를 함께 통과 | 필드별 최종값과 근거 |
| 5 | 장비 전체의 옵션 누락과 합계를 검사 | 경고가 없던 사진까지 완전 일치 여부를 판정 | 저장 가능한 공통 리뷰 |
| 6 | 실제 앱 흐름과 별도 자료를 검증 | 회귀·실제 Worker·단일/일괄/후보·저장·취소 확인 | 검증 보고서와 개발 반영 후보 |

### 1 정답표와 실패 관측

개발자가 이번 원본 19장의 실제 표시값을 읽어 필드별 정답표를 작성한다. 분류·필수 수치·반복 잠재 줄·요구 조건·화면에 없는 항목을 구분한다. 기존 정답표의 장비명은 자료 식별·과거 결과 대조용으로 보존하되 합격 판정에는 사용하지 않는다. 정답표는 평가에만 사용하고 런타임 파서나 모델에서 참조하지 않는다. 이미지와 정답표는 Git 제외 경로에 두고 입력 hash로 자료를 고정한다.

기존 `0927_equipment`와 과거 요구치 실험 원본 20장을 회귀 자료로 준비한다. 이미지 hash로 중복을 정리하고 실제 고유 장수를 확인하며, 단순히 19+19+20을 독립 표본 수로 합산하지 않는다. 과거 합성 56사례와 그중 잘못 채택된 8사례도 별도 반례 집합으로 재현한다. 파일이 없으면 기존 보고서 숫자를 현재 재현 결과로 대신하지 않고 자료를 복구하거나 다시 생성한다.

각 재판독에 사진·작업·행·보기 식별자, 원본 crop, 항목 후보, 원문, 좌표, 파싱 결과, 실행 실패/건너뜀 사유와 처리 시간을 남긴다. `mergeRecognitionRetry`가 파싱 실패 결과를 최종 옵션에 합산하지 않는 기존 안전성은 유지하면서, 실패한 결과도 별도의 관측 목록에는 보존한다. 중복 보기와 취소 후 늦은 결과는 유효 근거로 세지 않는다. 임시 관측은 사진 검토 세션에 한정하고 영구 저장 형식은 바꾸지 않는다.

현재의 6장 무경고·13장 16줄과 엄격한 필수 정보 일치율을 따로 측정한다. 개발자가 수동 대조하는 것은 검증 작업이며 사용자에게 필드를 고치게 하는 제품 흐름을 만들지 않는다.

### 2 미식별 줄의 재인식 대상 선택

현재처럼 정상 옵션으로 파싱된 줄만 재인식 후보로 삼는 조건을 없애는 방향으로 설계한다. 숫자/% 형태가 보이는 미식별 본문 행, 알려진 라벨과 유사한 행, 요구 조건 영역에서 라벨이나 값이 빠진 행도 위치 근거를 바탕으로 검토한다. 숫자가 읽히지 않더라도 지원 옵션의 라벨이 보이면 누락 후보에 포함한다.

항목명 사전과 제한된 글자 유사도는 **어디를 다시 읽을지 찾는 힌트**로만 쓴다. 후보 항목을 실제 인식값으로 치환하거나 원래 숫자와 결합해 확정하지 않는다. 후보가 여러 개이면 행 전체를 다시 읽고, 그래도 모호하면 실패 사유를 반환한다. 미지원 옵션을 가장 가까운 지원 항목으로 강제 변환하지 않는다.

원본 설명창 좌표에서 행 전체와 항목명/구분자/값 열의 위치를 보존한다. 인접 요구 조건·옆 열·다음 잠재 줄이 crop에 섞이지 않는지 검사한다. 발견 상자가 불완전하거나 원본 끝에 닿은 경우는 별도 실패로 기록한다. 파일명·아이템별 좌표를 사용하지 않는다.

완료 기준은 이번 14줄의 미식별 문제가 재인식 대상 선정에서 사라지고, 기존 2줄을 포함한 16줄의 처리 경로가 모두 설명되는 것이다. 이 단계에서 대상으로 선택된 것은 정확한 값이 복구됐다는 뜻이 아니다.

### 3 항목명과 참고 항목의 판독

원색 행 전체, 휘도를 보존한 행, 항목명 영역의 다른 배율을 비교한다. 현재 두 기본 판독에 공통 적용하는 강한 흰색 마스크가 반복 오독을 만들 수 있다는 것은 확인할 가설이며, 전처리별 실제 모델 결과를 대조한 뒤 판단한다. 개발 자료에서 개선된 보기 순서를 고정하고 별도 평가 자료에는 그 순서를 바꾸지 않는다.

원본을 다시 읽어 올스탯·DEX·요구 레벨 등의 항목명이 실제로 식별되는지 확인한다. 전체 행의 의미와 항목명 영역의 결과가 충돌하면 숫자를 채택하지 않는다. 허용 별칭과 미식별 상태를 분리하고, 짧은 영문 라벨이나 여러 글자의 오독을 문자열 치환만으로 해결하지 않는다.

방어력·MP 같은 참고 항목은 원본 재판독으로 그 의미가 확인된 경우에만 계산용 미지원 옵션과 구분한다. 이때 계산 입력에 해당 수치를 넣지 않으며, 참고 수치의 판독 여부는 내부에 남긴다. 물리 방어력과 방어율 무시처럼 계산 적용 여부가 다른 항목을 구분하는 반례를 포함한다. 단순히 알 수 없는 4줄을 무시하거나 경고를 숨기는 방식은 사용하지 않는다.

현재 막힌 참고 항목 4줄의 의미가 정확히 확인되면 해당 항목 때문에 계산 장비 등록을 막을 이유가 없어야 한다. 참고 항목 수치의 정확도와 등록 필수값의 정확도는 결과표에서 구분한다. 필수 항목과 참고 항목 중 어느 쪽인지 불명확한 행은 계속 보류한다.

### 4 숫자와 퍼센트 검증

정상 항목명과 원본 행의 위치를 확인한 뒤 숫자·부호·%를 포함한 값 영역을 검증한다. 전체 행과 값 영역을 함께 관찰해 라벨이 잘못 연결된 숫자, 인접 행의 숫자, 앞뒤 글자가 잘린 결과를 구분한다. 원본 색상·휘도 보존·배율의 일치는 필요한 관측이지만 그 자체가 정답 증명은 아니다.

숫자 0과 빈 값, 고정값과 %, 반복 옵션, 두 열 요구 조건을 분리한다. 글자가 숫자로 보인다는 이유로 허용하지 않은 문자나 누락된 %를 자동 보정하지 않는다. 기존 O/B 정규화는 원래 허용 문맥에서만 유지한다. 파싱되지 않는 숫자 조각도 충돌·불완전 근거로 보존한다.

첫 판독과 새 판독이 충돌할 때 다수결로 덮어쓰지 않는다. 원본 글자 범위·행 대응·단위가 온전히 검증된 경우에만 최초 탐색값을 대체할 수 있는 규칙을 실험한다. 대체한다면 초기 오독과 최종값, 사용한 원본 근거를 모두 남긴다. **최초 숫자 충돌을 대체하는 규칙은 새 구현 제안이며 현재 D-150 기본 동작을 이미 변경한 것이 아니다.** 근거가 부족하면 사용자 보정 없이 완료했다고 표시하지 않는다.

과거 희미한 첫/끝 숫자, 일부 획이 사라진 숫자, 같은 값으로 반복되는 오답, 잘린 %를 실제 모델로 재현해 판정한다. 양쪽 crop의 단순 좌표 완전성이나 OCR confidence 점수만으로 합격시키지 않는다. 글자 전체가 검출됐는지를 판정하는 보조 근거도 정상 게임 사진과 정보 손실 반례 양쪽에서 검증해야 한다.

현행 모델과 보기 변환으로 이 기준을 만족하지 못하면 활성화 조건을 완화하지 않는다. 기존 로컬 Tesseract Adapter나 브라우저에서 실행할 수 있는 별도 숫자 판독 후보를 제한된 실험에서 비교한다. 다른 엔진과의 일치도 정답 보증으로 삼지 않으며 실제 정답표와 반례로 평가한다. 새 모델의 구체적인 선정·라이선스·WASM 동작·용량은 그 조사 단계에서 공식 자료와 실행 결과로 확인한다. 현재 계획은 엔진 교체나 새 모델 도입을 확정하지 않는다.

### 5 장비 전체의 누락 검사

이번 16줄만 복구하면 끝내지 않는다. 실제 사진에 표시된 지원 항목이 최초 탐지에서 통째로 사라지거나 두 배율에서 같은 오답이 나온 경우도 평가한다. 경고가 없던 6장을 포함해 19장 전부를 정답표로 채점한다.

설명창 상단부터 마지막 옵션까지의 원본 범위를 확인하고, 기본 옵션과 잠재 영역의 물리적인 행을 대응시킨다. 같은 이름의 잠재가 반복되면 원래 줄 수만큼 합산하며 재판독 횟수만큼 합산하지 않는다. 항목명이 읽혔는데 값이 빠졌거나 값만 읽혀 항목이 사라진 행은 누락 후보로 남긴다. 모든 장비가 같은 필드 목록을 갖는다는 고정 템플릿을 만들지 않는다.

새 게임 UI의 합계 뒤 구성값, 여러 열 요구치, 상단 공격력 증가량은 별도 자료로 검증한다. 공격력 증가량을 장비 공격력에 합산하지 않고, 이미 포함된 강화/구성값을 다시 더하지 않는다. 강화 수치의 포함 관계가 근거로 확인되지 않은 UI는 호환 성공으로 선언하지 않는다. 관련 미확정 사항은 기존 결정 기록 D-OCR-NEW-UI-001을 따른다.

전체 그림에서 글자 정보가 실제로 잘렸거나 가려졌으면 값을 만들어내지 않는다. 시스템의 자동 재시도 후에도 원본 정보가 부족하면 해당 사진을 실패로 기록하고 촬영 문제를 설명한다. 선명한 원본의 모델 오독을 촬영 문제로 전가하지 않는다.

### 6 앱 통합과 평가 자료 확장

검증된 복구 결과를 기존 공통 `OcrReview`에 연결한다. `reviewText`, `mapReviewedStats`, `reviewQuestions`, `reviewBlocked`가 같은 최종값과 동일한 근거를 사용해야 한다. 자동 복구를 사용자가 확인한 `confirmed`로 위장하지 않으며 초기 판독을 다시 조립할 때 복구 근거가 사라지지 않도록 한다.

단일 장비 등록, 여러 장 등록, 구매 후보에서 실제 브라우저 Worker와 모델을 실행해 같은 장비 값이 나오는지 확인한다. 기존 프리셋·직업별 저장 키·장착 목적지·펜던트 선택·저장 실패 보존을 유지한다. 사진 변경·영역 변경·직업 전환·불러오기·취소 시 오래된 복구 근거와 늦은 결과가 적용되지 않아야 한다.

이번 19장은 모두 개발에 사용한 자료다. 이를 다시 통과해도 독립 평가로 부르지 않는다. 이전 게임 사진은 회귀 집합, 위치 이동·배율·압축을 바꾼 자료는 파생 집합, 개발에 쓰지 않은 새 실제 사진은 별도 평가 집합으로 나눈다. 폰트·해상도·배경·캡처 방식별 결과를 기록한다. 2026-10-01 후속 답변에서 사용자가 이번19장의 게임 설정을 돋움(Dotum)으로 확인했으므로, 알려진 이전 Noto Sans 자료와 구분해 검증한다. 굴림이나 다른 UI의 별도 실제 자료를 확보하지 못하면 그 범위는 미검증으로 남긴다.

각 집합에서 잘못된 자동 채택과 기존 성공 회귀가 한 건이라도 있으면 해당 규칙의 기본 적용을 보류하고 원인을 수정한다. 실패 사진을 분모에서 빼거나 자동 차단을 성공으로 합산하지 않는다. 이후 사용자 3~5명 POC에서는 개발자가 조작을 돕거나 OCR 값을 고쳐주는 일이 없이 등록·저장·후보 비교를 완료해야 한다.

## 현재 구조를 활용하는 방법

새 UI별 복구 규칙을 만들지 않는다. 인식 Module이 원본 행을 찾고 판독 근거와 최종 리뷰를 반환하며, 기존 `batchReview`는 그 리뷰를 받아 장비를 배정한다. `saveBaselineSetup`은 성공한 적용값의 준비·검증·저장과 실패 상태 보존을 계속 담당한다. 직업 저장 맥락과 계산 정책을 판독 오독 해결에 섞지 않는다.

| 기존 위치 | 계획한 책임 |
|---|---|
| `ocr/types.ts` | 필드/참고/미식별 대상, 모든 복구 시도, 원본 출처, 최종 판정의 임시 타입 |
| `ocr/retryRecognition.ts` | 파싱 성공 여부와 분리된 대상 선택, 항목 후보, 행/값 영역의 대응 |
| `ocr/requirementView.client.ts` | 원본 영역의 보존·보기 생성·인접 필드 침범과 잘림 검사 |
| `ocr/recognizePaddle.client.ts` | 기존 엔진 수명과 취소를 유지하며 판독 의존성을 복구 Module에 제공 |
| 복구 Module의 신규 파일 | 대상 탐색·제한된 재판독·관측 보존·필드별 검증을 한 Interface 뒤에 모음 |
| `ocr/verifyRequirementRecovery.ts` | 기존 미통과 실험 상태 유지. 일반화하기 전에 반례 재현과 판정 재설계 |
| `ocr/reviewRecognition.ts` | 원시 판독과 검증된 최종값을 분리해 공통 리뷰를 생성 |
| `ocr/batchReview.ts`와 `saveBaselineSetup.ts` | 기존 최초/재시도 배정과 저장 보호를 재사용 |

복구 Module의 제안 Interface는 `recoverEquipmentReview(review, context, recognize): Promise<OcrReview>`다. `context`는 원본 사진·작업 식별자·취소 신호를 포함하고, `recognize`는 현재 엔진의 실제 판독 의존성이다. 호출자와 테스트는 이 Interface를 사용한다. 모델 내부 점수나 각 보기의 충돌 예외를 UI가 다시 조립하지 않는다. 구체적인 타입과 파일명은 구현 시 확정하며 이 문서에서 새 공용 계약을 기정사실로 만들지 않는다.

복구 Module 안의 순수 판정은 DOM·저장·엔진 실행 없이 관측 자료를 받아 채택/미해결과 이유를 반환한다. 원본 숫자 충돌·참고 항목 혼동·복제된 증거를 이 판정으로 테스트하고, 실제 브라우저에서는 Interface를 통해 이미지·Worker·취소·최종 리뷰를 함께 확인한다. 복구 Module을 없애면 대상 선택과 판정 지식이 인식기와 세 화면으로 퍼지게 되는 책임을 모으는 것이 목적이다.

## 처리 시간과 자원 제한

인식한 정상 줄을 무조건 반복해서 읽지 않고 미식별·충돌·누락 위험과 검증 정책에 따라 필요한 행을 선택한다. 두 초기 판독이 같은 오답을 냈다는 반례 때문에 초기 일치만으로 모든 고위험 필드의 검증을 생략하지는 않는다. 시간 증가와 필수 정보 정확도 이득을 함께 비교해 확정한다.

같은 Paddle Worker를 재사용하고 보기 결과를 같은 원본/작업/행에서만 재사용한다. 같은 이미지를 다시 읽은 횟수를 독립 증거로 부풀리지 않는다. 중복 복구 경로와 실패 재시도의 무한 반복을 막는다. 기존 최대 12줄·8보기 제한을 먼저 기준으로 측정하며, 제한을 바꾸는 경우 이유와 비용을 기록한다. 한도를 초과한 미해결 행을 조용히 생략하지 않는다.

실험용 다른 엔진은 미해결 행의 제한된 비교에서만 준비한다. 모든 사진/병렬 Worker에 추가 모델을 무조건 로드하지 않는다. 최초 로딩, 반복 판독, 사진 1장과 실제 일괄 처리의 메모리·실행 시간을 분리한다. 측정 전에는 처리 시간 개선이나 임의의 초 단위 SLA를 약속하지 않는다.

시간과 메모리를 비교할 때는 같은 기기·브라우저·Worker 수를 사용하고 동시 빌드나 다른 인식 실험을 중지한다. 개발 자료에 맞춰 보기 순서나 임계값을 조정한 뒤에는 별도 평가 자료에서 이를 다시 조정하지 않는다.

## 검증과 기본 적용 조건

| 검증 계층 | 필수 확인 |
|---|---|
| 순수 판정 | 미식별 라벨, 여러 후보, 모호한 숫자, 단위 누락, 참고/전투 혼동, 같은 원본/행/필드·중복 보기 |
| 실제 모델 반례 | 두 판독의 같은 오답, 희미하거나 잘린 앞/뒤 숫자와 %, 초기 오독+후속 올바른 판독, 인접 행 혼입 |
| 개발 원본 | 19장 전체 필수 정보·반복 옵션 합계·무보정 결과 |
| 이전 원본 회귀 | 자료 hash로 고정한 기존 정상 결과의 유지와 미해결 결과 구분 |
| 별도 실제 자료 | 개발에 사용하지 않은 사진과 폰트/배경/배율 조건별 결과 |
| 앱 동작 | 단일·일괄·구매 후보, 실제 Worker, 저장 실패·취소·늦은 결과·복원·직업 키 보존 |

구현 시 관련 회귀·타입·lint·두 빌드와 전체 테스트를 실행한다. 전체 테스트의 기존 실패가 있으면 같은 기준 소스와 대조해 이번 회귀와 분리하고, 전체 통과로 표현하지 않는다. 기존 구조 개선의 테스트 통과는 새 정확도 규칙의 실제 이미지 검증을 대체하지 않는다.

실험은 기존 리뷰를 바꾸지 않는 진단 경로에서 시작한다. 정답표·반례·별도 자료의 오채택 0건과 기존 성공 회귀 0건, 이번 19장 무수정 완전 일치 목표를 모두 만족한 후보만 기본 연결 대상으로 정한다. 일부만 복구하면 그 단계의 성과와 남은 실패를 보고하며 전체 완료로 선언하지 않는다. 후보가 실패하면 기존 기본 경로를 유지하고 관측 자료로 다음 실험을 설계한다.

잘못된 기본 규칙을 되돌릴 때 저장된 사용자 값이나 최초 판독 증거를 함께 지우지 않는다. 복구 근거는 영구 저장하지 않고 기존 숫자 저장 형식·원본 입력 호환을 보존한다.

## 산출물과 반영 범위

계획 수행 시 산출물은 비공개 정답표/입력 manifest, 판독별 실패 관측, 대상 선정 결과, 복구 Module과 반례 회귀, 실제 모델 비교표, 장비별 완전 일치 채점표, 앱 통합 검증 보고서다. 공개 문서에는 사진·원문 대신 집계·조건·한계와 코드 위치를 남긴다.

계획 작성은 이 문서와 결정 기록으로 완료한다. 앱 구현·새 규칙 활성화·엔진 교체는 아직 진행하지 않았다. 후속 구현 요청은 비운영 작업 브랜치에서 수행하며, `dev-main` 개발 반영과 `main` 운영 반영은 기존 사용자 요청 범위에 따라 구분한다. 운영 배포·외부 OCR/LLM 전송·유료 서비스·새 모델 도입을 계획 작성 요청에서 승인된 것으로 해석하지 않는다.

근거 문서는 [인식 검증 기준](ocr-validation.md), [미통과 요구치 실험](ocr-verified-recovery-plan.md), [구조 개선 보고서](architecture-paar-report.md), [도메인 용어](../CONTEXT.md)다. 실행/결정 상태는 DECISIONS.md의 최신 기록을 따른다.

## 첫 구현 결과와 남은 작업

`recoverEquipmentReview`는 미식별 본문 행과 기존 검토가 놓친 요구 조건 라벨을 재인식 대상으로 선택한다. 완전한 crop·출처·작업·행·보기 식별자, 실제 판독의 값/단위/항목 일치, 다른 행/필드 혼입, 원래 숫자와의 충돌을 검사한다. 제안 문자열은 적용값이 아니며, 불완전 숫자 조각은 차단 근거로 보존한다. 수동 수정/제외·요구 조건 직접 수정은 해당 복구 근거를 무효화한다.

일반 Paddle 경로에는 기존 재시도의 성공·파싱 실패·보기 미생성·실행 실패 관측을 추가했다. 숫자 적용·저장 정책은 유지한다. 실험 Module은 기존 요구치/전투 옵션의 복구를 먼저 보존하고 그 뒤 남은 행을 대상으로 실행한다. `experimentalEquipmentRecovery`를 명시한 개발 호출에서만 관측/후보 적용을 시험할 수 있고 일반 브라우저 팩토리·제품 UI에는 설정하지 않는다. 기존 미통과 요구치 실험과 동시에 실행하지 않는다.

원본19장의 기본 경로 재검증은 후보/호출 오류0·13장16줄 확인 필요로 이전과 같았다. 이는 관측 추가가 기존 값/차단을 바꾸지 않았다는 확인이며 정확도 개선 완료가 아니다. 정답표를 포함한 엄격한 평가에서는 요구 조건 누락과 경고 없는 필드 오독도 확인했으므로, 무경고 장수를 성공률로 계산하지 않는다.

후속 수치 확인은 저장된 실제 브라우저 판독 결과를 정답표와 다시 대조한 것이다(새 추론·일괄 저장 시험이 아니다). 요구 조건을 포함한 수치 전체와 분류가 일치한 사진은1/19장(5.3%), 장비명까지 전체 일치하고 확인 줄이 없는 엄격한 완전 인식은0/19장이다. 최초 판독에서 읽힌 장비명은 review.header가 아닌 반환 문자열에 남을 수 있어 현행 tooltipHeader로 반환 문자열도 검사했으며, 이번 결과에는 유효한 장비명이 없었다. 확인 줄이 없는6장(31.6%)을 성공6장으로 세지 않는다. 목표는 해당 개발 자료19/19장·잘못된 자동 채택0·사용자 보정0이며 별도 실제 자료/POC를 통과한 결과로 확대하지 않는다.

원색·휘도·회색·완만한 대비·배율·보간·검출 영역과 입력 크기를 바꾼 실제 판독, 기존 로컬 Tesseract, 한국어 v3 후보와 EasyOCR 계열 후보를 비교했다. 기존 모델의 올스탯 오독이 반복됐고 추가 모델도 수치 정확도 기준을 충족하지 못했다. 해당 모델 파일은 Git 제외 실험 경로에만 있으며 배포 자산이나 새로운 제품 의존성으로 추가하지 않았다.

돋움 후보는 설치된 글꼴로 만든 일반 항목명과 무작위 숫자만 학습했다. 원본19장·개인 정답표는 학습에 사용하지 않았다. 브라우저 ONNX 판독에서 일부 올스탯·영문 스탯·참고 항목 이름은 개선됐지만 숫자의 오독과 정보 손실 판정 오류가 남았다. 합성 검증 정확도나 항목명 성공을 장비 전체의 정확도로 표현하지 않는다. 학습 코드·관측·모델은 Git 제외 `output/ocr-accuracy-implementation/`에 보존했다.

다음 단계는 숫자의 실제 글자 전체와 단위를 검증하는 근거, 돋움 실제 이미지의 배경/행 분리 조건, 전체 옵션/요구치 누락 검사를 보강하는 것이다. 현재 원본 숫자 충돌을 무조건 덮어쓰거나 정보가 부족한 값을 추측하는 규칙은 구현·활성화하지 않았다. 남은 실패를 해결하고 기존 원본·정보 손실 반례·별도 자료의 오채택0/정상 회귀0 기준을 통과한 후에만 기본 적용을 다시 판단한다.

### 1 원색 보존을 기본 비교축으로 둔다 — 최우선

현재 대비식에서는 RGB 중 하나라도135 이하이면 출력이 흰색으로 포화된다. 예를 들어 가상의 빨간 픽셀 `(255,80,80)`은 `(255,255,255)`로 바뀐다. 이는 대비식으로 확인되는 정보 손실 가능성이지 해당 게임 사진의 실패 원인을 새로 증명한 사례가 아니다. 밝은 흰 글자를 강조하는 같은 처리를 장비명·등급·색상 숫자에 일괄 적용하면 위험하다.

추천 비교는 원색, 휘도 보존/필요 시 반전, 현재 대비의 세 가지다. 색상 행은 RGB 채널 최솟값 대신 휘도 또는 밝기/채도·주변 배경과의 차이를 이용하는 후보를 검토한다. 단순 채널 최댓값 처리도 밝은 배경을 글자로 살릴 수 있으므로 정답 후보로 기정사실화하지 않는다. 색상 마스크는 영역 탐색을 도울 수 있지만 최종 판독에는 원본 글자 획과 숫자·단위를 보존한다.

Paddle의 기본 입력은 색상 채널을 가진 이미지와 모델의 정규화다. Tesseract의 밝은 배경/어두운 글자 권고를 Paddle 전체의 필수 조건으로 확대하지 않는다. 원색도 이전에 시험한 후보이므로 이번의 핵심은 두 초기 보기에서 정보 손실이 반복되는지와 필드별 효과를 대조하는 것이다. [Paddle 인식 코드](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/paddleocr-js/packages/core/src/models/rec.ts), [Tesseract 전처리 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html).

### 2 행·열 분리와 글자 전체를 보존하는 crop — 최우선

요구치의 다중 열, 본문 옵션, 반복 잠재, 장비명과 설명 문장을 분리해 평가한다. 먼저 같은 행의 항목명·값·단위를 함께 보존하고, 필요한 경우에만 원본 가로 위치와 구분자를 근거로 항목명/값 영역을 추가 분리한다. 줄의 앞·뒤 숫자, `+`, `-`, `%`, 소수점·콜론을 포함한다. 항목명 조각과 다른 행 숫자를 조합하지 않는다.

검출 box가 실제 획을 포함하는지, 상하 여유가 인접 행을 섞는지, 반복 잠재를 한 줄로 합치는지, 테두리/구분선을 글자로 읽는지를 검사한다. 여백은 실제 배경과 어울리게 생성하되, 검출 후 행 crop이 다시 만들어지므로 바깥 canvas에 여백을 넣었다는 사실만으로 인식 모델의 여백이 보장되는 것은 아니다. 원본→보기→검출 box→행 crop 좌표를 보존한다.

`unclip_ratio` 확대는 잘린 획을 포함할 수 있지만 인접 글자·행도 합칠 수 있다. crop의 물리적 완전성을 먼저 확인하고 변수 하나씩 비교한다. Tesseract 공식 문서는 너무 빽빽하거나 과도하게 큰 여백의 문제를 설명하고, Paddle은 검출 영역 확장 비율을 노출한다. 실제 플래닛에 효과가 있는 여백값은 아직 확정하지 않았다. [Paddle 검출 안내](https://www.paddleocr.ai/main/en/version3.x/module_usage/text_detection.html), [SDK 다각형 crop](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/paddleocr-js/packages/core/src/pipelines/ocr/crop.ts), [Tesseract 여백 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html).

### 3 원본에서 직접 확대하고 모델 입력을 확인한다 — 높은 우선순위

첫 비교는 동일한 원본 crop에서 만든2배/3배와 nearest/linear 보간이다. 이 중 성과가 있는 조합에 한해4배·cubic을 추가한다. 확대본을 축소하거나 이미 대비로 획을 잃은 보기에서 또 보기들을 만들면 원본 정보가 돌아오지 않는다. pixel 글꼴은 nearest가 유리할 수 있고 안티앨리어싱 글자는 linear/cubic이 유리할 수 있지만, 어느 방식도 돋움 숫자의 정답을 보장하지 않는다.

OpenCV는 일반적인 축소에 AREA, 확대에 LINEAR/CUBIC을 안내한다. 이는 시각적 보간의 일반 권고이며 게임 OCR 최적값은 아니다. DPI 메타데이터를300으로 변경하는 것과 실제 글자 픽셀을 늘리는 일도 다르다. Tesseract의300DPI 안내를 한국어 Paddle 모델의 최적 글자 크기로 옮기지 않는다. [OpenCV 크기 조정](https://docs.opencv.org/4.x/da/d54/group__imgproc__transform.html), [Tesseract 확대 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html).

같은 원본에서 검출 입력 크기, 검출 누락/잘림, 최종 인식 crop,48px 정규화 후 글자의 높이와 획을 관측해야 한다. Paddle의 `limit_type=min`/큰 입력 조정 안내는 전처리 후보의 근거지만, 좁고 긴 행에서960을 그대로 쓰면 긴 변 제한·메모리 비용과 함께 작동하므로 전역 적용하지 않는다. 현재 SDK는 인식 crop을 종횡비에 따라 조정한다. 문서의 고정 폭 숫자를 근거로 임의로 글자를 가로 늘이거나 잘라내지 않는다. [Paddle 검출 크기 안내](https://www.paddleocr.ai/main/en/version3.x/module_usage/text_detection.html), [SDK 인식 크기 조정](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/paddleocr-js/packages/core/src/models/rec.ts).

### 4 배경이 불균일한 행에만 약한 국소 대비를 비교한다 — 중간 우선순위

CLAHE는 주변 영역별로 대비를 조정하고 증폭 한도를 두는 방법이다. 반투명 툴팁 뒤의 배경이나 희미한 글자에서 원색/휘도만으로 대비가 충분하지 않은 경우의 후보로 적합하다. 전역 대비와 달리 국소적으로 조정하지만 배경 무늬·노이즈도 커질 수 있다. 휘도에 약하게 적용한 후보와 원색을 비교하며, `clipLimit=1~2`는 실험 시작점일 뿐 채택값이 아니다. [OpenCV CLAHE 안내](https://docs.opencv.org/4.x/d5/daf/tutorial_py_histogram_equalization.html).

Otsu·adaptive threshold·Sauvola는 글자와 배경을 흑백으로 나누는 후보다. 배경이 균일하면 Otsu, 위치별 밝기가 다르면 국소 threshold 계열을 비교할 근거가 있다. 그러나 Paddle에서 전처리 이진화가 항상 유리하다는 공식 보장은 없으며, 작은 `%`의 점·한글 내부 획·희미한 숫자가 지워질 수 있어 기본 전역 이진화의 우선순위는 낮다. Tesseract5의 Sauvola 지원도 별도 엔진 기능이다. [OpenCV threshold 안내](https://docs.opencv.org/4.x/d7/d4d/tutorial_py_thresholding.html), [Tesseract 이진화 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html).

반투명 툴팁의 배경은 보통 캡처 시 이미 픽셀에 합성된다. PNG alpha를 제거하거나 임의의 흰 배경으로 합성한다고 원래 게임 배경이 분리되지는 않는다. 투명 파일의 alpha 처리 문제와 합성된 배경의 대비 문제를 별개로 취급한다.

### 5 노이즈·굵기·기울기 보정은 해당 결함이 있는 경우에만 비교한다 — 후순위

median/약한 노이즈 제거는 압축 잡음이 있는 입력에서 비교한다. lossless 원본 스크린샷에 일괄 blur를 넣으면 한 픽셀 획·`:`·`%`가 약해질 수 있다. erosion/dilation/opening/closing도 글자 획의 축소·확대나 작은 구조 제거를 포함하므로 전역 적용하지 않는다. 한글 자모 연결이나8/0 내부 공간이 달라지면 판독이 악화될 수 있다는 위험 가설을 함께 채점한다. [OpenCV 형태 연산 안내](https://docs.opencv.org/4.x/d9/d61/tutorial_py_morphological_ops.html), [Tesseract 노이즈·굵기 안내](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html).

인게임 직접 캡처는 수평 UI를 기준으로 하며 회전/원근 보정은 실제 기울기 증거가 있을 때만 사용한다. 이미 SDK의 다각형 crop에서 원근 변환이 일어나므로 수평 원본을 거듭 변형하지 않는다. 가능한 경우 무손실 원본을 내부 기준으로 사용하고 원본 JPEG/WebP를 PNG로 다시 저장한 것을 손실 복구로 표현하지 않는다.

텍스트 전용 초해상도는 저해상도 자연 장면 OCR에 대한 연구 근거가 있다. 그러나 TextZoom에서의 성과는 플래닛의 작은 한글/숫자/% 성과가 아니며, 복원된 보기의 판독만으로 원본에 없는 획을 확정할 수 없다. 현재 목적에서는 후순위의 별도 모델 실험으로 두고 처리시간·배포 자산·정보 손실 반례까지 평가해야 한다. [ECCV2020 원 논문](https://www.ecva.net/papers/eccv_2020/papers_ECCV/html/1186_ECCV_2020_paper.php).

### 시험 순서와 판정 방법

| 순서 | 비교할 변수 | 핵심 판정 |
|---|---|---|
| 기준 | 현재 경로·고정 모델/SDK·같은 원본 정답표 | 경고 없는 오독/누락까지 포함한 현행 결과와 관측 고정 |
| A | 현재 대비 ↔ 원색 ↔ 휘도 | 색상/흰색·항목명/값/단위별 오독·누락 비교 |
| B | 기존 crop ↔ 행/열 분리와 글자 전체 crop | 첫/끝 glyph·인접 행 혼입·누락·반복 잠재 대응 |
| C | 원본 직접2/3배 × nearest/linear | 최종 인식 입력의 획과 실제 필드/장비 정답 비교 |
| D | 실패한 불균일 배경 행의 약한 CLAHE | 기존 정상 회귀·%/숫자 손실·추가 시간 비교 |
| 추가 | 앞 단계에서 이유가 확인된 경우만4배/cubic·국소 이진화·굵기 보정 | 새로운 오채택이 생기면 기본 적용 제외 |

행 단위로 검출 실패, 잘림/다른 행 혼입, 항목명 오독, 숫자 오독, 단위 손실, 파서/재인식 연결 실패를 구분한다. 비교마다 모델·폰트·원본·기기·브라우저·배율·보간·실제 입력 크기와 시간을 고정/기록한다. 최초 모델 준비시간과 준비 후 판독시간도 분리한다. 필터를 모두 조합해 최고 신뢰도 결과를 고르는 방식은 개선 근거가 아니다.

기존19장은 개발 자료로 사용하고 Noto Sans·굴림의 기존 정상 자료와 앞/뒤 숫자·%가 희미하거나 잘린 반례를 회귀로 포함한다. 최종 조합과 임계값을 고정한 뒤 별도 실제 돋움 자료를 평가한다. 동일 원본의 확대/압축 파생본은 개발/평가 집합에 나눠 넣지 않는다.

주 지표는 장비 단위 무수정 완전 일치율이며 숫자·% 오채택, 필수 정보 누락, 정상 회귀, 사용자 보정 횟수·추가 시간/메모리를 따로 보고한다. 이전에 같은 모델의 여러 보기가 숫자 손실을 같이 놓친 반례가 있으므로 보기 일치·다수결·높은 신뢰도를 원본 검증의 대체로 쓰지 않는다. 작은 표본의 오채택0건도 모든 환경의 안전을 증명하지 않는다. 기존 계획의19/19장·오채택0·정상 회귀0·별도 자료 평가 기준은 유지한다.

조사 결론은 **원색 보존 → 행·열 분리와 crop 완전성 → 원본 직접 확대/모델 입력 대조 → 필요한 행의 약한 대비** 순서다. 전처리 후 글자가 선명하고 완전한데도 같은 항목명/숫자를 계속 오독하면 해당 모델의 글꼴 대응이나 후처리·대상 연결을 별도 과제로 분류한다. 전처리만으로 전체 무수정 목표를 달성할 수 있다고 약속하지 않는다.

## 미해결 인식값 복구 설계 구체화 — 2026-10-09

상태: 사용자 요청에 따른 문제 정의·개발 설계 초안. 아래 내용은 이번에 새로 구현하거나 정확도 검증을 통과한 기능이 아니다. 기존 기본 판독·비활성 실험·실패 이력을 보존하며, 과거 결과를 새 실행 결과로 표시하지 않는다.

### 문제 정의

**사진 등록을 자동화했지만 OCR의 항목명 오독·숫자/단위 충돌·옵션 누락이 남으면 사용자가 장비 정보를 다시 고쳐야 한다.** 오류값 적용 차단은 계산 보호 수단이며, 이 작업의 개선 대상은 원본에서 정보를 회복해 수동 보정을 줄이는 과정이다. 원본에 없는 숫자를 추측하거나 경고를 제거해 복구로 세지 않는다.

### 현재 구현과 이번 설계의 차이

| 이미 있는 처리 | 현재 한계 | 이번에 구체화할 설계 |
|---|---|---|
| 기본 두 판독과 최대12행·행당8보기 재시도 | 항목명을 특정하지 못하면 기본 재시도 대상으로 진입하지 못할 수 있음 | 항목명 성공 여부와 분리한 행 인벤토리·실패 유형·복구 경로 선택 |
| 원색/휘도/회색/약한 대비의 확대 보기 | 같은 모델·변환이 같은 숫자 오답을 반복할 수 있음 | 항목명·숫자·단위를 분리한 관측과 오답 반례 중심의 채택 평가 |
| `recoveryObservations`와 실험용 `recoverEquipmentReview` | 기능은 이미 있으나 일반 UI에서 실험은 비활성이고 정확도 기준 미통과 | 관측/출처 계약을 재사용하고 새 복구 전략을 관측 전용으로 비교 |
| 최초 숫자 충돌 보존 | 추가 판독이 맞아도 충돌을 자동 해소하지 못함 | 최초값 대체는 별도 검증된 규칙에 한정하고 대체 근거와 이전 원문을 보존 |
| 검출된 행·파싱된 옵션의 검토 | 처음부터 검출되지 않은 줄은 미해결 목록에도 없을 수 있음 | 지원 옵션·반복 잠재·요구치의 누락을 확인하는 장비 전체 검사 |

근거는 `recognizePaddle.client.ts`, `retryRecognition.ts`, `recoverEquipmentReview.ts`, `reviewRecognition.ts`의 현재 코드다. 과거19장16줄 중14줄의 재시도 미진입과 숫자 손실 반례8/56 오채택은 앞선 저장된 실험 이력이며 이번 재측정이 아니다. 원색 보기·확대·다중 엔진·돋움 합성 학습을 처음 제안하는 신규 해결책으로 소개하지 않는다.

### 1. 원본과 좌표를 끝까지 연결

현재 `recoverEquipmentReview`에는 전체 업로드 원본이 아니라 `prepared` 설명창 파일이 전달된다. 이미 잘린 설명창 바깥의 글자는 이 파일만 다시 잘라 복원할 수 없다. 준비 단계에서 다음 정보를 함께 유지하는 `SourceFrame` 계약을 실험 경로에 추가한다.

- 업로드 원본 File 참조, 준비된 설명창 File 참조와 두 이미지 크기.
- 실제 적용한 정수 픽셀 crop 사각형, 자동 inset 여부, 준비 좌표→원본 좌표 변환.
- 이미지/작업 식별자와 변환 버전. 선택 영역·사진 변경 시 기존 근거 무효화.

`prepareTooltipImage`의 직접 실행과 Worker 응답이 같은 좌표 정보를 제공해야 한다. 계산기 저장 형식에는 추가하지 않고, 파일을 불필요하게 복제하지 않는다. 원본 파일에 글자가 남아 있을 때만 준비 영역/행 영역을 넓혀 재판독한다. 업로드 원본 자체에서 잘렸거나 가려진 경우는 복구 불가능 후보로 구분하되, 선명한 원본의 모델 오독을 촬영 문제로 분류하지 않는다.

### 2. 항목명이 아닌 실패 유형으로 복구 경로 선택

현재 사용자용 `reason` 문장과 별도로 실험용 원인 코드를 둔다. 하나의 행에 여러 원인이 있을 수 있으므로 단일 문자열 하나로 조기 확정하지 않는다.

| 원인 코드 제안 | 관측할 근거 | 실행할 복구 |
|---|---|---|
| `label-unreadable` | 행 위치는 있으나 항목명이 파서에 연결되지 않음 | 행/항목명 영역을 별도로 읽고 사전은 후보 범위 제한에만 사용 |
| `value-conflict` | 같은 행에서 서로 다른 숫자를 관측 | 원본의 값 영역과 행 전체를 따로 읽어 라벨·숫자·단위 대응 확인 |
| `unit-conflict` | 고정값/% 판독이 충돌하거나 단위 영역이 잘릴 가능성 | 숫자 오른쪽 단위 영역까지 포함해 재판독; %를 규칙만으로 추가하지 않음 |
| `crop-incomplete` | 준비 영역/행 영역이 원본의 글자 영역을 자름 | SourceFrame으로 원본에 돌아가 행/열 경계를 보존한 영역 재생성 |
| `row-unaccounted` | 본문 글자 영역과 OCR/파싱 행 대응이 빠짐 | 해당 위치 재탐지·재판독 후 장비 전체 누락 검사로 연결 |
| `runtime-failed` | 모델/보기 생성 실패·취소·예산 초과 | 글자 오독과 분리해 재시도 가능 여부 기록; 실패를 빈 값 동의표로 취급하지 않음 |

행 인벤토리와 미검출 영역 탐지는 픽셀 정보만으로 완전성을 보증하는 판정기가 아니다. 줄 간격·연결 요소 등의 후보를 실제 정답표로 평가하고, 반복된 같은 잠재 옵션을 하나로 합치지 않도록 좌표 기반 행 식별을 유지한다.

### 3. 항목명과 값의 판독 책임 분리

재판독 결과를 곧바로 `올스탯 +6%` 같은 한 문자열로 병합하지 않고 임시 후보를 `항목명 / 숫자 / 단위 / 원본 영역 / 관측 출처`로 분리한다. 문법·허용 범위는 불가능한 후보를 제외하는 데 사용하며, 가장 그럴듯한 숫자를 채우는 데 사용하지 않는다.

- 항목명 후보: 기존 파서/별칭을 재사용하되 유사 문자열은 재판독 경로를 찾는 힌트로만 사용. 원본 재판독 없이 `올스탯`으로 강제 치환하지 않음.
- 값 후보: 숫자·부호·소수점·%를 포함한 값 영역을 보존. 전체 행의 라벨과 원본 좌표로 연결하며 다른 행의 숫자를 가져오지 않음.
- 보조 판독 후보: 과거 돋움 후보는 일부 항목명이 개선됐지만 숫자는 미통과였으므로, 재사용한다면 항목명 판독으로 역할을 제한해 별도 비교. 기존 Tesseract/다른 모델의 실패를 무시한 엔진 교체는 하지 않음.
- 조합: 같은 이미지·작업·행의 후보만 조합. 같은 숫자/단위의 반복 판독도 독립 정답 증거로 세지 않음. 이름만 성공한 결과는 필드 전체 복구로 집계하지 않음.

예를 들어 항목명만 잘못 읽힌 `...? +6%`와 숫자 자체가 충돌하는 `DEX +8`/`DEX +80`은 다른 실험으로 다룬다. 첫 사례는 항목명 복구의 개선분을 분리해 검증할 수 있지만, 두 번째는 이름 사전만으로 해결할 수 없다.

### 4. 복구 판단과 최초값 대체

기존 `recoverEquipmentReview`를 재사용하되 대상 선정·원본 영역 생성·판독·순수 판정을 내부 단계로 나눈다. 단일/일괄/후보 UI가 복구 규칙을 각각 구현하지 않도록 같은 최종 리뷰를 받게 한다. `evaluateEquipmentRecovery`의 현행 최초 숫자 충돌 거부 규칙을 이름만 바꿔 제거하지 않는다.

복구 판정에는 유효한 동일 행 근거, 라벨/값/단위의 대응, 다른 숫자·부분 숫자·실패 판독을 포함한 모든 관측, 취소/변경/출처 검사가 필요하다. 이는 필수 조건이며 실제 정답의 충분조건은 아니다. 특정 전략의 자동 채택 허용 여부는 정답표·정보 손실 반례·별도 실제 이미지 평가로 결정한다.

최초값을 대체하는 전략은 특히 분리해서 검증한다. 새 판독의 횟수나 점수가 높다는 이유만으로 덮어쓰지 않는다. 원본 행/값 영역의 관측과 전략별 오류 분석으로 기존 판독을 대체할 조건을 정의하고, 모든 관측·대체 사유·전략 버전을 기록한다. 조건을 검증하지 못한 숫자 충돌은 이 단계에서 해결했다고 표시하지 않는다.

### 5. 장비 전체 검사와 사용자 흐름

필드 복구 후에도 분류·요구치·지원 옵션·반복 잠재의 개수·단위와 원본 행 대응을 검사한다. 장비명 일치 검사는 2026-10-10 최신 결정으로 성공 조건에서 제외한다. '화면에 없음'·'검출했으나 읽지 못함'·'지원하지 않는 참고 정보'를 구분하며 미인식을0으로 채우지 않는다.

사용자에게는 기존 검토 데이터를 유지한 채 자동 재인식 진행 상태를 보여주는 방식을 제안한다. 복구에 성공한 필드만 같은 최종 리뷰에 반영하고 저장은 기존 정책을 따른다. 원본 정보가 부족하면 필요한 캡처 범위를 구체적으로 안내하되 재촬영도 개입/실패로 집계한다. 원본이 충분한데 모델이 못 읽으면 모델 한계로 기록하며 임의 숫자 입력을 정상 성공으로 세지 않는다.

### 첫 개발 단위와 검증 순서

1. **원인별 재현 자료:** 기존 관측/정답표를 재사용해 라벨 오독·숫자 충돌·단위 손실·영역/행 누락을 분류. 경고가 없던 사진도 포함. 개인 원문은 Git 제외 자료에만 보관.
2. **SourceFrame과 실패 분류:** 준비 이미지의 원본 좌표 연결 및 typed issue를 관측 전용으로 구현. 기본 리뷰/적용값과의 동일성 및 취소·이미지 변경 검증.
3. **항목명/값 분리 실험:** 숫자·단위가 일치하지만 항목명만 미해결인 사례부터 분리 판독을 비교. 여기서 전체 필드가 정확해진 비율과 기존 정상 회귀를 채점. 숫자 충돌 전체를 해결했다고 확대하지 않음.
4. **숫자·단위/누락 실험:** 값 영역·단위·원본 재영역 설정·행 인벤토리를 각각 별도 비교. 현행 판독기로 해결되지 않으면 관측이 가리킨 실패 유형에 한해 보조 모델 실험을 재설계.
5. **선택적 적용:** 먼저 관측 전용으로 비교하고 각 전략의 정답·회귀·비용을 확인한 뒤 제한적으로 적용. 미통과한 기존 두 실험 옵션을 기본 활성화하지 않음.

초기 비용 비교에서는 모델·문자 배치6·같은 Worker/기기를 고정한다. 기본 재시도와 새 복구가 동일 영역을 중복 판독하지 않도록 하나의 예산에서 관리하며 기존 최대12행·8보기와의 비용 차이를 기록한다. 속도 유지·정확도 보존·메모리 절감을 별도 측정하고 임의의초 단위 SLA를 확정하지 않는다.

장비 단위 무수정 완전 일치, 필드별 복구 정확도, 잘못된 자동 채택, 미검출/단위 누락, 정상 사진 회귀, 사용자 보정/재캡처, 전체 완료시간·메모리로 평가한다. 과거19장은 개발 집합이며 원본의 파생 이미지를 별도 평가 집합에 나눠 넣지 않는다. 자동 채택 후보는 기존 오채택0·정상 회귀0 및 별도 자료 평가 기준을 유지한다. 이번 설계만으로 이 기준을 충족한 것은 아니다.

### 기술 참고와 적용 범위

2026-10-09에 [Tesseract 품질 개선 문서](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)의 처리 입력 확인·영역/행 분리·적절한 여백 설명과 [OpenCV 임계처리 문서](https://docs.opencv.org/4.13.0/d7/d4d/tutorial_py_thresholding.html)의 전역/국소 임계처리 차이를 확인했다. 이는 원인에 맞는 입력을 조사하는 참고이며 Paddle에서의 성공이나 새 필터 도입 효과를 보장하지 않는다. 이번 제안은 같은 필터를 반복 적용하는 방식과 구분해 원본 좌표·실패 유형·필드 판독 책임을 구체화한다.

브라우저 내부 실행, 원본/사용자 입력/저장 호환 보존, 외부 OCR/LLM 전송 금지, 미통과 자동 적용 비활성 원칙을 유지한다. 이번 섹션은 설계 초안이며 앱 코드·모델·정책·운영 배포 변경이나 성능/정확도 실험을 수행하지 않았다.

### 첫 구현 진행 기록 — 2026-10-09

사용자의 후속 구현 요청으로 첫 단계 구현·실제 브라우저 실험을 시작했다. **진행 중이며 미인식 해결 완료나 새 자동 복구의 기본 활성화 완료가 아니다.** 위 설계 시점의 미구현 설명은 당시 이력으로 보존한다.

### 첫 범위 구현 — 원본 근거를 가진 항목명 복구

처리 흐름은 **원본 좌표 유지 → 실패 분류 → 전체 행·항목명 분리 재판독 → 원본 글자 대조 → 검증된 필드 반영**이다. 숫자·단위가 안정적인데 항목명만 읽히지 않는 경우가 이번 범위이며, 숫자 충돌·요구 조건·미검출 행 전체를 해결하는 구현은 아니다.

`recoverLabels.ts`가 단일·일괄·구매 후보에서 사용하는 공통 인식 경로의 마지막 리뷰를 만든다. 장비 분류 아래 본문만 대상으로 삼고, 앞선 재시도가 사용한 행은 중복 판독하지 않는다. 최대12행에서 전체 행/항목명과 원색/휘도의4보기를 사용한다. 모든 최초 숫자·단위와 전체 행 재판독이 일치해야 하며, 이미지·작업·행·보기·판독ID 및 원본 영역을 검사한다. 실패·숫자 조각·충돌을 동의표에서 누락하지 않는다.

항목명 판정은 다음 세 경로를 구분한다.

1. **분리 재판독 일치:** 전체 행과 항목명4보기에서 같은 허용 항목명을 실제로 읽은 경우.
2. **픽셀 근거 복구:** 재판독의 한글 항목명에서 한 글자만 어긋난 경우 후보를 만든 뒤, 원본의 콜론으로 이름 영역을 분리해 브라우저 글꼴 렌더링과 대조. 허용 항목뿐 아니라 각 글자의 초성·중성·종성 대체 후보를 함께 비교한다. 다른 글자를 공통으로 잘못 읽을 수 있으므로 관측이 어긋난 글자만 비교하지 않는다. 전체 유사도0.75 이상, 경쟁 후보와의 차이 및 구별되는 픽셀의 근거를 함께 검사한다. 근접 후보에 대해서는 정규화된 오차 차이0.5 이상을 요구한다.
3. **전체 행 명칭과 픽셀의 결합:** 출처가 검증된 전체 행에서 정확한 항목명이 읽혔고, 픽셀 비교도 같은 명칭을 단독1위로 선택한 경우. 전체 유사도0.75 이상을 유지하고 모든 근접 후보보다 픽셀 오차가 작아야 한다. 이 경로는 픽셀 단독 판정과 구분해 `source-row-label-and-glyph-agreement-v1`로 남긴다. 텍스트 명칭이나 픽셀 후보가 충돌하면 복구하지 않는다.

문자열 유사도는 후보 탐색에만 사용하며 최종값으로 치환하지 않는다. 글꼴·크기·간격은 이미지 대조의 후보이며 실제 게임 글꼴의 확정값이 아니다. 원본 숫자·%는 새로 예측하지 않고, 기존 큰 고정 스탯·크리확률 등의 검토 규칙도 다시 적용한다. 원문 관측과 선택 판독ID, 픽셀 후보 점수, 복구 사유를 보존한다. 항목명 안에 완전히 포함된 중복 획 기호만 판정에서 제외하며, 원문에서 삭제하거나 전체 행의 숫자·부호를 필터링하지 않는다.

픽셀 후보는 최대256개, 글자 영역과 공개 글꼴 캐시에는 크기/용량 제한을 두고 후보 사이에서 취소를 확인한다. 공개 어휘 템플릿 캐시는16MiB 이내이며 작업 종료 시 정리한다. 파일은 임시 참조이고 저장 형식에 넣지 않는다. 사용자가 합산 수치를 직접 바꾸면 관련 자동 복구 근거를 무효화하며, 요구 스탯 수정으로 보너스 스탯을 덮어쓰지 않는다.

기본 팩토리는 이 항목명 복구를 실행한다. 비교 실험에는 `labelRecovery: false`, 관측 전용에는 `labelRecovery: "observe"`를 사용한다. 기존 미통과 `experimentalRequirementRecovery`와 `experimentalEquipmentRecovery`는 자동으로 켜지지 않으며 별도 실험과 동시에 실행하지 않는다. 모델·문자 배치6·계산·저장·이미지 경고 정책은 유지한다.
