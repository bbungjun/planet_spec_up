# 익명 오류 제보와 운영자 관리

일반 이용자는 계산기 상단 `오류 제보`에서 제목·오류 유형·내용을 작성한다. 사용 환경은 선택 입력이다. 제보 창은 새 탭으로 열려 기존 계산기와 임시 후보를 유지한다. 접수가 성공하면 접수 번호만 표시한다. 제보 목록·본문·운영자 메모는 운영자 로그인 후에만 조회한다.

## 운영자 사용

`/feedback/admin`에서 운영자 비밀번호로 로그인한다. 제목·본문·운영자 메모 검색, 처리 상태 필터와 이전 제보 조회를 제공한다. 각 제보의 `처리 상태·운영자 메모`에서 접수 / 확인 중 / 수정 완료 / 종료와 수정 내역을 저장한다. 제보 삭제는 확인 창을 거치며 영구 삭제다.

세션은 12시간이며 HttpOnly·SameSite=Strict 쿠키를 사용한다. HTTPS 운영에서는 Secure를 추가한다. 비밀번호를 교체하면 기존 세션도 무효화된다. 쿠키·비밀번호·DB 토큰을 코드, 결정 기록, 커밋에 넣지 않는다. 비밀번호는 공유하지 않는 무작위 값을 권장한다. 이 로그인은 운영자에게만 필요하며 계산기나 익명 접수의 가입 조건이 아니다.

다른 탭에서 같은 글을 수정하면 오래된 내용으로 덮어쓰거나 삭제할 수 없다. 새로고침 후 변경된 글의 `최신 내용 불러오기`를 눌러 편집 기준을 갱신한다. 현재 작성 중인 메모는 먼저 보존한다.

## 로컬 실행

저장소/워크트리 루트에 Git 제외 파일 `.env.local`을 만든다.

```dotenv
FEEDBACK_ADMIN_PASSWORD=24자이상256자이하의운영자전용비밀번호
```

무작위 비밀번호 생성 예시:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

`npm run dev`는 기존 Vinext 개발 경로다. 제보용 로컬 D1 바인딩 `FEEDBACK_DB`를 자동 제공하고 `.wrangler` 아래에 데이터를 저장한다. 기존 Sites의 DB 바인딩 설정과 개인 세팅에는 영향을 주지 않는다.

Vercel과 같은 Next.js 경로는 다음과 같다.

```powershell
npm run build:vercel
npm run start:vercel -- --port 3004
```

원격 DB 설정이 없는 로컬 Next에서는 `output/feedback/reports.sqlite`에 저장한다. 로컬 Vinext D1과 Next SQLite는 서로 다른 시험 저장소다. 원격 DB 주소를 설정하면 두 실행 경로 모두 그 DB를 사용한다. 로컬 저장소, `.env*`, `.wrangler`, `.playwright-cli`와 `output`은 Git에 올리지 않는다. 로컬 DB를 삭제하면 제보도 사라진다.

## 운영 연결과 배포 전 점검

Vercel은 서버 파일의 영구 저장을 보장하지 않으므로 운영에서는 로컬 SQLite를 사용하지 않는다. [Vercel 공식 설명](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel)

구현은 HTTPS로 접속하는 원격 libSQL DB를 지원한다. Turso/libSQL SDK를 선택한 것은 에이전트의 구현 선택이며 새 유료 계정이나 특정 요금제의 사용자 승인으로 해석하지 않는다. 실제 계정·DB 생성·비용·운영 토큰 발급·연결 시험은 아직 수행하지 않았다. [공식 SDK 문서](https://docs.turso.tech/sdk/ts/reference)

Vercel 서버 환경 변수에 다음 값을 설정한다. `NEXT_PUBLIC_` 접두사를 붙이지 않는다.

| 환경 변수 | 값 |
| --- | --- |
| `FEEDBACK_ADMIN_PASSWORD` | 충분히 무작위인 24~256자 비밀번호 |
| `FEEDBACK_DATABASE_URL` | `libsql://...` 또는 `https://...` 원격 DB 주소 |
| `FEEDBACK_DATABASE_TOKEN` | 해당 DB에 접근하는 서버 전용 토큰 |

운영자 설정이 없으면 익명 접수도 성공으로 표시하지 않는다. Vercel에서 원격 주소·토큰이 없거나 로컬 파일/HTTP 주소를 지정하면 503으로 차단한다. 저장 실패도 성공 접수로 표시하지 않으며 입력을 유지한다. 실제 데이터 저장이 완료된 경우에만 접수 번호를 반환한다. 처음 연결할 때 서버가 `feedback_reports`, `feedback_limits`와 인덱스를 생성하므로 토큰에 스키마 생성·읽기·쓰기 권한이 필요하다. 장비 세팅 스키마는 사용하지 않는다.

Preview와 Production에는 별도 DB·비밀번호·토큰을 지정해 시험 글이 운영 데이터에 섞이지 않게 한다. 코드 빌드는 DB 설정 없이도 가능하다. 운영 DB 연결 뒤 익명 작성 → 별도 운영자 브라우저 조회 → 상태/메모 저장 → 로그아웃 접근 차단을 다시 검증한다. 운영 게시판 사용 준비와 공개 배포는 이 검증 후에 판단한다.

작업 브랜치 푸시는 소스 보관이다. `main` 병합·푸시, `vercel --prod`, 운영 환경 설정·반영은 D-146의 명시적 공개 반영 요청 범위에서만 실행한다.

## 저장 정보와 접근 제한

저장하는 것은 접수 번호·오류 유형·제목·본문·선택 입력 환경·처리 상태·운영자 메모·접수/수정 시각이다. 이름·연락처를 요구하지 않고 개인 장비 세팅, 스크린샷, 인식 원문, 브라우저 저장값, User-Agent를 자동 수집하지 않는다. 현재 사진 첨부는 제공하지 않는다. 제보는 삭제 전까지 서버에 남으며 백업·보존 기간 정책은 후속 운영 설정 사항이다. 사진 전송/보관 범위는 별도 결정 없이 확장하지 않는다.

서버는 JSON 크기 24KB, 제목 5~100자, 본문 10~4,000자, 선택 사용 환경 200자, 운영자 메모 4,000자를 제한한다. 텍스트는 HTML로 실행하지 않고 SQL 값도 바인딩한다. 익명 작성에는 목록/상세 읽기나 기존 글 수정 권한이 없다. 접수 결과는 ID만 반환하며 실패 응답에 DB 오류 원문·비밀정보를 포함하지 않는다. 관리 API는 인증을 확인하고 응답 캐시를 금지한다. 페이지와 API는 검색 색인을 막는다.

중복 제출과 통신 응답 유실을 대비해 같은 입력의 재시도는 같은 UUID를 사용한다. UUID는 접수 식별자이며 공개 조회 권한이 아니다. 같은 글을 재시도하면 중복 삽입이나 추가 접수 한도 소모 없이 접수 결과를 돌려준다.

남용 방지는 공유 DB의 트랜잭션으로 처리한다. 익명 접수는 같은 접속 IP 기준 10분 고정 구간당 5건, 전체 시간당 100건을 허용한다. 운영자 로그인은 같은 접속 IP의 15분 구간당 8회, 전체 시간당 300회로 제한한다. 통신/DB 장애 시 이 제한을 우회해 성공 처리하지 않는다. 여러 서버 인스턴스가 같은 카운터를 공유하며 제보 생성과 한도 검사가 원자적으로 실행된다.

IP는 글에 저장하지 않는다. 서버 비밀번호를 키로 한 HMAC을 한도 키에만 사용하고, 만료한 한도 기록은 다음 쓰기에서 정리한다. Vercel에서는 플랫폼이 덮어쓰는 `x-forwarded-for`를 사용한다. 로컬 Node에서는 사용자가 보낸 전달 헤더를 신뢰하지 않고 하나의 로컬 버킷으로 처리한다. [Vercel 요청 헤더 문서](https://vercel.com/docs/headers/request-headers)

현재 제한은 초기 구현값이다. 독립 사용자 검증, 대규모 부하·봇 공격 검증이나 처리량 보장을 의미하지 않는다. 공개 후 실제 제보량과 운영 비용을 확인해 조정한다.
