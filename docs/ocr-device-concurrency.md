# 기기별 브라우저 OCR 동시 처리 검증

## 문제와 검증 범위

사용자 문제: 사용자의 RAM 용량, CPU 성능, 다른 프로그램의 사용량이 다를 때, 브라우저 안에서 장비 사진 OCR을 몇 개씩 처리해야 메모리 부담과 대기 시간을 함께 줄일 수 있는가?

최적화 대상은 모델 파일 크기만이 아니라 브라우저 전체의 최대 메모리, 처리 완료 시간, 취소/종료 뒤 남는 자원이다. 장비 단위 인식 결과·누락·숫자/% 검증과 사용자 저장 정책은 유지한다. 빠른 오인식은 성공이 아니다.

2026-10-07 요청으로 비교 실험을 진행한다. 앱 기본 정책을 바꾸지 않고, 같은 앱 OCR 경로를 로컬 전용 계측 서버에서 실행한다. 이 문서는 기술 검증 자료이며 사용자 결정 원장은 `DECISIONS.md`다.

## 브라우저가 알 수 있는 것의 한계

- `navigator.deviceMemory`는 개인정보 보호를 위해 근사·제한된 총 RAM 힌트다. **현재 남은 RAM이나 탭의 메모리 예산이 아니다.** 미지원 브라우저도 있다. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory)
- `hardwareConcurrency`는 사용 가능한 논리 프로세서 수의 힌트이며 CPU 세대·클럭·메모리 대역폭·현재 부하를 나타내지 않는다. 브라우저가 실제보다 적게 보고할 수도 있다. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/hardwareConcurrency)
- `performance.memory`는 비표준 JS 힙 정보로, Worker·WASM·이미지 메모리를 포함한 브라우저 전체 RAM의 대체값이 아니다. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)
- 메인 스레드 타이머가 매끄럽게 동작해도 별도 OCR Worker가 많은 메모리를 쓸 수 있다. UI 지연만으로 RAM 여유를 판단하거나 OOM을 사전에 확실히 잡을 수 없다.
- 현재 제품의 메모리 미보고 시8GB 가정, 압축 파일 바이트만을 이용하는 동시 처리 제한은 재검토 대상이다. 이미지 픽셀 상한24M 검사는 별도로 이미 존재한다. 디코딩 후 검사이므로 최초 디코딩 자체의 피크까지 막는 것은 아니다.

## 분리해서 비교할 가설

1. 동일 문자 배치6에서 인식기3/2/1의 속도와 최대 메모리를 비교한다. 각 인식기는 검출·문자인식 모델과 런타임을 독립 준비한다.
2. 인식기 수를 고정한 채 문자 배치6/3/1을 비교한다. 같은 동시 처리 수에서 중간 텐서 크기를 줄이는 효과를 본다.
3. SDK 실험 사본에서 글줄 crop과 전처리 Float32Array를 필요한 추론 묶음만 생성·해제한다. 먼저 원래 crop의 기하/회전 규칙으로 크기만 계산하고 정규화 폭별로 안정 정렬한다. 원래 패딩·추론 그룹·출력 순서를 유지한다. 초기 도구 작성 때 Float32Array만 묶음 생성하는 안을 준비했으나, SDK 실험을 시작하기 전에 crop까지 같은 묶음으로 제한하도록 확장했다. 사진 원본 Mat·검출 모델과 모든 추론 중간 버퍼까지 스트리밍했다는 의미는 아니다.
4. SDK 재빌드 자체의 영향을 구분하기 위해 **설치된 SDK → 소스 복원 무변경 대조군 → Float32Array 생성 시점만 변경한 실험군**을 비교한다. 대조군이 제품 출력과 다르면 채택을 중단한다.
5. 처리 후/취소 후 인식기가 종료되고 늦은 결과가 들어오지 않는지 확인한다. 프로세스의 잔류 메모리만으로 누수라고 결론내리지 않는다.
6. 첫3개 동시 처리의 최고 Private Bytes가 첫 사진 완료 전 초기 준비·초반 추론 구간에 나타난 것을 근거로, 인식기 수3/문자 배치6을 유지하면서 모델 초기화만 직렬화한 경우를 추가 비교한다. 세부 이벤트상 초기화 완료 뒤에도 메모리가 상승하므로 초기화만이 원인이라고 단정하지 않는다. 먼저 준비된 인식기는 다음 모델이 초기화되는 동안 판독할 수 있다. 이 가설은 첫 관측 후 추가한 탐색 실험이며 사전 확정 가설로 소급하지 않는다.

기기 사양 값을 임의로 바꾸는 것은 정책 분기 시험일 뿐 실제 저사양 기기 성능 검증이 아니다. CPU 제한도 실제 저RAM 환경을 재현하지 않는다. 이번 PC의 결과를 다른 기기 최적값으로 일반화하지 않는다.

## 재현 도구

루트에서 다음 명령으로 로컬 전용 계측 서버를 시작한다. `--fixtures`에는 PNG/JPEG/WebP만 든 비공개 폴더를 지정한다. 이미지는 이 PC의 루프백 서버와 격리 브라우저에서만 처리한다. 제품 서버/저장값·node_modules·모델 파일은 수정하지 않는다.

```powershell
node scripts/ocr-memory/serve.mjs --port=3007 --variant=installed --fixtures=output/ocr-concurrency-20260928/fixtures
```

다른 터미널에서 설치/캐시된 Playwright CLI를 사용한다. 처음에는 `npx @playwright/cli --help`로 CLI를 준비하고 필요한 브라우저 설치 안내를 따른다. 각 trial은 새 격리 브라우저이며 이름을 재사용하지 않는다. 세션은 완료/실패 시 닫는다. 다른 실험 폴더를 쓰려면 서버의 `--output`과 runner의 `-Output`을 같은 Git 제외 경로로 지정한다.

```powershell
./scripts/ocr-memory/run.ps1 -Trials @('3x6','1x6','2x6') -Prefix a
./scripts/ocr-memory/run.ps1 -Trials @('2x6','1x6','3x6') -Prefix b
./scripts/ocr-memory/run.ps1 -Trials @('3x3','3x1') -Prefix batch
./scripts/ocr-memory/run.ps1 -Trials 3x6 -Prefix serial -Init serial
node scripts/ocr-memory/summarize.mjs
```

SDK 비교는 기존 계측 서버를 종료한 뒤 `--variant=control` 또는 `--variant=stream`으로 다시 시작하고 서로 다른 trial prefix로 실행한다. SDK 소스는 설치된0.4.2의 sourcemap에서 Git 제외 output 안으로 복원한다. 버전/소스 anchor가 달라지면 자동 적용하지 않고 오류를 반환한다. 생성 코드는 원저작권 표시를 유지하며 제품 번들에 포함하지 않는다.

## 측정 조건

- 입력 파일 SHA-256, 앱 OCR 관련 소스/모델 SHA-256, Git HEAD, 실제 브라우저 사양 힌트와 이미지 크기를 저장한다. 사용자 사진/인식 원문은 Git 제외 output에만 남긴다.
- 사진 File 준비 및 모델 HTTP캐시 예열 후 시작한다. 엔진 초기화는 측정에 포함한다. **최초 네트워크 다운로드 시간과 실제 사용자 검토·저장은 제외**한다.
- Windows에서 시험 CLI 프로세스의 자식 브라우저 프로세스를 추적해 Working Set/Private Bytes를 합산한다. 약0.5초 대기+CIM 조회 간격으로 표본화하므로 순간 피크를 놓칠 수 있다. Working Set의 공유 페이지가 중복될 수 있으며 OCR 모델 단독 메모리가 아니다.
- 시작 전 기준값, 전체 피크, 완료/취소 후5초의 관측값을 분리한다. 강제 GC는 사용하지 않는다. main-thread JS heap은 보조 지표다.
- 시스템 여유 RAM3GiB 미만 또는 시험 브라우저 Working Set6GiB 초과에서 취소하고,10분 경과도 중단한다. 이는 로컬 실험 중단선이며 제품의 보장값이 아니다. 이 자원 확인은 OS 도구로 하므로 일반 웹앱에서 그대로 사용할 수 없다.
- 결과 비교는 입력별 반환 텍스트·장비명·필드·줄 상태·검토 사유·경고를 비교한다. 가변 시간·좌표·신뢰도·실행ID는 제외한다. **기존 판독과 동일함은 정답과 일치함을 뜻하지 않는다.**
- 실행 도중 다른 설정의 OCR·빌드·테스트를 병렬 실행하지 않는다. 다른 앱과 OS 부하는 완전히 통제되지 않는다.
- 실제 시험 브라우저는 HeadlessChrome154이며 CPU20논리 프로세서/RAM32GiB 힌트를 보고했다. 실제 앱의 모든 카드 렌더링·사용자 조작을 포함하는 시험이나 다른 브라우저/저사양 실기 시험이 아니다.

## 결과와 정책 판단

### 설치된 제품 SDK의 첫 반복 실험

동일 Noto Sans 사진19장(각1833×1031), i5-13600KF/32GiB, 문자 배치6에서의 관측이다. 순서는3→1→2, 다음2→1→3이다. 시간은2회 평균, 메모리는2회 중 관측 최대다.

| 동시 인식기 | 전체 시간 평균 | Working Set 최대 | Private Bytes 최대 | 브라우저 발급 결과 해시 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 165.37초 | 1.71GiB | 1.70GiB | 각19/19 기준 일치 |
| 2 | 94.51초 | 2.36GiB | 2.47GiB | 각19/19 기준 일치 |
| 3 | 75.33초 | 3.78GiB | 4.44GiB | 각19/19 기준 일치 |

이 첫 반복 구간에서3→2개로 줄이면 시간은약25.5% 늘고 관측 최대 Working Set은약37.4%, Private Bytes는약44.2% 줄었다. 관측 최대값끼리의 비교이며 모든 기기의 절감률이나 RAM 보장값이 아니다. `a-2x6`의 ASCII 시간/자원 수치와 브라우저 SHA-256은 온전하지만 저장 원문의 한 항목은 아래 수집기 결함으로 무효다. 원문 검증은 온전한 `b-2x6` 및 수정 후 재실행과 구분한다.

배치3/1은 추출 수치·장비명·차단 여부·검토 항목 수가 기준과 같았지만, 원문/줄 결과와 검토 안내 내용2/3장이 달랐다. 숫자 오답 증가나 정확도 개선으로 단정하지 않는다. 추론 그룹과 패딩이 달라지는 설정을 단순한 무손실 성능 옵션으로 취급할 수 없다는 결과다.

SDK를 소스로 복원한 무변경 대조군의 시간도70.46초에서165.91초로 변했다. 설치된 제품 SDK 재실행 `c-3x6` 역시157.35초로 느려졌다. CPU/RAM 힌트는 같았으며 원인은 이 실험에서 분리하지 못했다. 따라서 초기 구간과 뒤쪽 구간의 시간을 섞어 평균을 내거나 글줄 묶음 처리의 속도 손해/이득으로 단정하지 않는다. 무변경 대조군·실험군과 설치 SDK를 구분해 보존하고, 추후 실행 환경과 빌드 형태를 통제한 비교가 필요하다.

한글 수신 수정 후 설치 SDK를 순서대로 다시 측정한 결과는 다음과 같다. 두 실행 모두 저장 원문 SHA-256 검사가 통과했고19장 모두 기준 결과와 일치했다.

| 뒤쪽 재검증 | 전체 시간 | Working Set 최대 | Private Bytes 최대 |
| --- | ---: | ---: | ---: |
| 3개·배치6 | 157.35초 | 3.59GiB | 4.22GiB |
| 2개·배치6 | 223.46초 | 2.31GiB | 2.38GiB |

뒤쪽 구간에서도2개는3개보다 관측 최대 WS가약35.6% 낮고 시간은약42.0% 길었다. 초기 구간의 절대 시간/비율을 기기별 보장값으로 쓰지 않고, **처리 수 감소의 메모리/시간 관계와 실측 변동을 함께** 기록한다.

### 수명·수집기 검증

- 같은 브라우저에서5장을2회 연속 처리해10건 모두 완료, 기준 출력 일치, 종료 시 소유 인식기0을 확인했다. 전체47.47초, WS최대2.13GiB였다. 장기간 누수 검증으로 확대하지 않는다.
- 3개 설정의 초기화 직렬화 중1초에 취소한 시험은약1.04초에 배치 종료, 결과 콜백0·소유 인식기0이었다. 종료 후5초 관측에서도 늦은 결과가 없었다. 실제 OOM을 유발한 시험이 아니며 모든 취소 시점/브라우저를 검증한 것은 아니다.
- 종료 후에도 브라우저 프로세스에는 기본 페이지·코드·캐시 등이 남는다. 프로세스 전체 메모리가 시작 전 수치로 즉시 복귀하지 않는 사실만으로 누수를 확정하지 않는다.
- 브라우저 발급 SHA-256을 저장 JSON에서 다시 계산해 `a-2x6`과 `streama`의 원문 한 항목씩이 달라진 것을 발견했다. 원인은 HTTP Buffer를 청크별 문자열로 변환하면서 한글의 UTF-8 바이트가 경계에서 끊긴 것이다. 원본 파일은 보존하고 `receipt-integrity-failed`로 표시한다. 수정된 수신기는 바이트를 모두 합친 뒤 한 번 디코딩하며 최대4MB를 바이트 기준으로 제한한다. 모든 UTF-8 분할 경계·1바이트 청크·크기 제한·비정상 JSON을 검사한 Node 회귀2개가 통과했다.
- `streama` 중 초기화하지 않는 SDK 설정 생성 확인을 Node에서 시도했다가 모델 asset 설정 오류로 종료한 약0.57초의 점검도 겹쳤다. 이 실행은 통제된 성능 채택 근거로 사용하지 않는다. 실제 이미지 추론이나 외부 이미지 전송은 하지 않았다.
- 브라우저 내부에서 계산된 SHA-256과 수치 측정은 한글 수신 결함과 별개였지만, 저장 원문 손상을 감추거나 다른 판독으로 치환하지 않는다. `summarize.mjs`는 원문 무결성을 별도 검사하고 실패 시 상세 원문 비교 결과를 만들지 않는다.

수집기 회귀는 `node --test scripts/ocr-memory/body.test.mjs`로 다시 실행할 수 있다. 앱 TypeScript 검사와 이 도구에 대한 ESLint를 통과했으며, 앱 전체 게임 계산 QA나 원본 정답 대조를 수행한 것으로 확대하지 않는다.

### 결론의 범위

가장 분명한 조절 수단은 **인식기 수**다. 첫 반복 구간에서2개는3개보다 메모리를 낮추면서1개보다 빨랐다. 하지만 같은 사양 힌트에서도 뒤쪽 실행 시간이 달라졌으므로, 특정 코어/RAM 숫자만으로 최적값을 확정할 수 없다. 제품의1~3개 기본 규칙, 문자 배치6, OCR 검토/저장 정책은 이번 작업에서 변경하지 않았다. SDK 수정안의 구현과 제품 채택을 구분한다.

원본 사진·OCR 원문·회차별 타이밍·프로세스 표본·해시·수신 무결성 결과는 Git 제외 `output/playwright/ocr-memory-20261007/`에 보관한다. `summary.json`과 `trial-*.json`, `resources-*.json`, `provenance-*.json`이 근거다. 현재19장에서는 확인 항목이 남는 사진4장이 있으며, 결과 일치를 장비 정답 정확도/무수정 성공/독립 사용자 POC로 표현하지 않는다.

최종 도구는 후속 재실행 때 서버 시작별 provenance 파일을 고유 시각으로 저장하고 trial에서 해당 파일을 가리킨다. 계측 코드 해시·브라우저 시작 시각·실제 SDK 요청 경로도 함께 남긴다. 앞선 회차에 없던 metadata를 소급 생성하지 않는다.

## 다음 제품 정책 제안 — 아직 기본 동작에 반영하지 않음

문제는 **브라우저가 정확한 여유 RAM을 모르는 상태에서, 기기와 입력의 메모리 부담을 보수적으로 제한하면서 OCR 대기 시간을 줄이는 것**으로 정리한다.

1. RAM 힌트가 없을 때8GB로 간주하는 현재 규칙을 우선 재검토한다. 미보고/미확인 환경에서는1개로 시작하는 안이 더 보수적이다. 코어 수가 많다는 이유만으로3개를 선택하지 않는다.
2. 동시 처리의 상한은 RAM 힌트·검증한 기기 범위·입력 이미지의 픽셀 수와 함께 정한다. 이번 PC의2개 처리 결과는 균형 후보이며 모든8GB/16GB 기기의 안전을 입증하지 않는다. 구체적인 RAM 구간별 상한값은 실기 검증 후 확정한다.
3. CPU 처리 속도와 화면 반응은 위 상한 **안에서** 처리량을 조절하는 보조 신호다. 첫 사진이 빨랐다거나 메인 스레드가 매끄럽다는 이유로 메모리 상한을 늘리지 않는다. 사진마다 글줄 수·재인식 횟수가 달라 첫 사진 시간만으로 기기 성능을 확정하지 않는다.
4. 압박이 의심되면 새 작업 투입을 줄이고 대기열을 유지한다. 해상도·판독 횟수·검토 조건을 무조건 낮춰 속도를 얻지 않는다. OOM을 항상 잡아 재시도할 수 있다고 가정하지 않는다.
5. 기존 중복 공유·인식기 재사용·입력 인덱스 기반 결과 적용·개별 실패 격리·취소 시 늦은 결과 차단을 유지한다. 원문과 사용자 저장을 외부로 보내지 않는다.

실제 다른 기기에서 다음 검증이 필요하다: 저RAM PC와8/16GB급 PC, RAM 정보 미제공 브라우저, 게임을 함께 실행한 상태, 큰 해상도/다른 폰트의 별도 사진. 동일한 비교 도구로 최대 Working Set/Private Bytes·처리 시간·실패/취소·원본 정답 일치를 각각 기록한다. 이 단계 전에는 '모든 기기에 자동 최적화 완료'로 표현하지 않는다.
